# Notchcast maintainer guide

**Notchcast** is a modified fork of [Tinycast](https://github.com/abue-ammar/tinycast) (AGPL-3.0; a modified version, as its section 5a requires us to state): upstream `main` plus a few commits of ours on top, arm64 builds signed with our own identity. Upstream's README is at [abue-ammar/tinycast](https://github.com/abue-ammar/tinycast#readme).

Every ~10 minutes a GitHub Actions workflow checks upstream `main`; once the keeper's review of the new upstream diff passes, it replays our commits onto it, builds and runs the tests, and moves `main` only when green; each upstream release is rebuilt the same way and published here under the same tag.

This file is `notchcast/README.md`, the maintainer guide. The public root `README.md` is generated from `notchcast/README.public.md`; its feature list sits between the `features:start` and `features:end` markers. `main` is the default branch. Feature work happens on branches off `main` and lands as linear commits (no merge commits). Upstream's Raycast extensions stay hidden ([docs/hidden.md](docs/hidden.md)).

Our commits:

- `Notchcast: read releases from kaczordodgers/notchcast`: the in-app updater reads this repo's releases.
- `Notchcast: remove upstream workflows`: none of upstream's workflows run here. The sync makes this commit afresh on every replay, so upstream workflow edits never conflict and new ones never land.
- `Notchcast: tooling` and later fixes: this folder and `.github/workflows/`.
- `Notchcast: bundle id app.notchcast, URL scheme notchcast, name Notchcast`: our own app identity (Debug: `app.notchcast.dev`, name Notchcast Dev; a per-task test copy is named from its bundle id, [fork-strings.md](docs/fork-strings.md#channel-name)). The in-app updater treats it as a development build and stays inert; `notchcast.update` installs releases.
- `Notchcast: generated files`, always last: the root `README.md` (from `notchcast/README.public.md`), `Tinycast.xcodeproj` (XcodeGen from `project.yml`) and, when our commits change `Scripts/raycast-runtime/`, `Tinycast/Resources/RaycastRuntime.generated.js`. The sync makes it afresh; our other commits never carry these files (replay drops them from each commit), so upstream edits to them never conflict. It also removes every path in `notchcast/prune-paths.txt` (upstream files the app does not need, e.g. `website/`), so upstream edits to them never conflict either. Edit `notchcast/README.public.md` or `project.yml`, never the generated files.

## Sync (`.github/workflows/sync.yml`)

- Upstream review gate (#871): `main` moves onto a new upstream commit U only after an agent review of the upstream diff `old..U` passed. The record is a commit status `REVIEW_CONTEXT` (`config.env`, `notchcast/upstream-review`) on U in this repository; only a status created by the repository owner's account counts (`ci.py upstream_review`), so no workflow token, the Actions bot included, can pass the gate, and the newest owner status wins. The plan job reads it before any job runs upstream's tree; without a success, `main` stays where it is and the run logs why. The main job reads it again right before it pushes `main` (`ci.py reviewed`) and pushes nothing unless it is still a success. Meanwhile the `stage` job (Linux, deploy key, no upstream code run) force-pushes the diff to `sync/upstream` on top of `sync/upstream-base` (the old upstream commit, both without `.github/workflows`, so no push or PR event runs any workflow and nothing reaches a Mac runner) and keeps one draft PR labelled `REVIEW_LABEL` (`upstream-sync`) between them, whose body holds the range, the commits, the diff stat and the exact `gh api` command that records the verdict. A newer upstream updates the same PR; once `main` holds its upstream, the next run closes it. The PR is never merged.
- Who reviews: the Notchcast keeper, on each new `upstream-sync` PR, runs `gate.py pick notchcast review --from sync/upstream` (the gate) and `gate.py pick notchcast review-kimi --from sync/upstream` (a second voice that does not block), each with [review/upstream-review.md](review/upstream-review.md), then records the gate's verdict from their own `gh` login: `gh api -X POST repos/<FORK_REPO>/statuses/<U> -f context=notchcast/upstream-review -f state=success|failure -f description='<verdict>'`. Reviewers never set it themselves. A release tagged on another upstream commit waits (plan logs a notice) until that commit gets its own review and status the same way. With a notify hook, `notchcast.kick` reports once per upstream commit that waits for this review.
- Rebase waits while a non-draft PR from this repo into `main` is open, for at most 12 hours from the oldest upstream commit not in `main`, then proceeds with a warning.
- A replay whose `main` lease is lost because `main` moved meanwhile (a landing or the generated-files push) ends green with a notice; the next Sync (that push, or kick within the hour) replays again.
- Started by `notchcast.kick` (below) when upstream `main` or its newest release changed, at least hourly, on a push to `main` except generated-only changes (`Tinycast.xcodeproj/project.pbxproj`, `Tinycast.xcodeproj/xcshareddata/xcschemes/Tinycast.xcscheme`, `Tinycast/Resources/RaycastRuntime.generated.js`, `README.md`), and by hand. GitHub's own `schedule` stays in the workflow but has never fired for this fork. Each run: if upstream `main` moved and its review passed, the plan job first replays our commits on Linux; a conflict is reported there without spending a macOS runner. Then `notchcast/ci.py replay` cherry-picks our commits (`merge-base(main, upstream/main)..main`) onto the new upstream `main`, builds Debug on a GitHub-hosted `xcode-27` runner and runs upstream's `Scripts/run-tests.sh`. Only when green does it update `main` with `--force-with-lease` on the `main` it started from. That workflow push and the review branches above are the only history rewrites allowed in this repo; nobody force-pushes by hand. A `main` commit without a green `notchcast/tested` status (a push) is built and tested as it is, and gets that status when green; unless a green PR build of this repository already built and tested its tree: after a green build the PR workflow uploads a `tested-tree-<tree>` artifact (the tree of the checked-out commit without the project, scheme and `README.md`, which CI regenerates or never tests; the Raycast runtime stays in, `ci.py tested-key`), and plan marks `main` tested from a live one whose run is a green `pr.yml` run of `FORK_REPO` (fork PRs never count) and closes the `notchcast-main` issue. Any miss or API error tests `main` as before.
- Every upstream release from `BASELINE_TAG` (`config.env`) on, whose tagged commit was reviewed whole (it is exactly the upstream commit `main` is built on, or carries the owner's own success `REVIEW_CONTEXT` status), is rebuilt from its tagged commit with our commits replayed onto it, tested, built Release for arm64, signed with `Notchcast Self-Signed` and published under the same tag, title and prerelease flag as `Notchcast-<version>.zip` and `.dmg`. Version and build number come from upstream's own zip; mirror versions stay unchanged; snapshots append a numeric revision. A tag on a mere ancestor of a reviewed U waits for its own review: U may delete what that commit added, so the review of `old..U` never showed it. Plan pins the tagged commit; the release job builds that commit and fails if upstream moved the tag since (`ci.py pin-tag`). For a tag on any commit other than the one `main` is built on, the release job reads that commit's review again before it tests or signs anything (`ci.py reviewed`) and fails unless the owner's newest status is still a success. The tag here names the replayed commit that was built, never upstream's tag object, so pushing it starts none of upstream's workflows.
- Tests: upstream's full suite except `HIDDEN_TESTS` (`config.env`), the harnesses of features Notchcast hides (`docs/hidden.md#harnesses`), and, on GitHub-hosted runners only, `CI_SKIP_TESTS` (`config.env`), harnesses the hosted VM cannot run (Vision OCR, rendered-text capture), which must still pass on a Mac. A harness that fails is run once more alone; if it still fails, it is run on the pristine upstream commit under our commits, and only a harness that passes there blocks (a failure on upstream too is upstream's flake or the VM, and is ignored with a warning).
- On a replay conflict, a red build or a red test nothing is pushed or published and `main` stays as it is. Land a hand resolution as `notchcast/replay-fixes/<name>.patch` (full diffs covering exactly the conflicting non-catalog, non-generated files, from the replay's current tip to resolved content; clean cherry-pick results are preserved; lowercase subject with non-alphanumeric runs replaced by hyphens, trimmed at both ends); delete it once Sync has rewritten main. When an older release tag needs a different resolution, add it as `<name>.<base label>.patch` (e.g. `<name>.v0-12-9-beta-134.patch`): the replay tries `<name>.patch` first, then the labelled ones in name order, and uses the first that applies; delete a labelled one once its release is published. A commit that still cherry-picks cleanly but breaks on the new upstream without a conflict (an upstream switch over our settings keys, a source an upstream file now needs) gets an adaptation instead: `notchcast/replay-adaptations/<name>.patch`, named the same way (labelled ones too), applied after that commit is picked, cleanly or by its replay fix; the first that applies is used, and one already in the commit counts as applied unless a copy of a hunk's old lines still remains in the file. The replay fails on that commit when such a copy remains, even where the file repeats those lines on purpose (accepted: the replay cannot tell which copy was meant, so quote enough context to make the hunk unique), and when an adaptation's quoted lines match nowhere, so it applies neither way, as once upstream edits a line it quotes; delete it once Sync has rewritten main. A red build or test is remembered as `refs/notchcast-failed/<main-<upstream>|release-<tag>|test>-<main>`, so it is retried only when upstream or `main` changes; a conflict is found again cheaply on Linux each run.
- Each failure opens or updates one issue per kind, closed by the next green run of that kind: `notchcast-sync` (replaying onto new upstream), `notchcast-main` (a pushed `main` tested as it is), `notchcast-release` (per tag). A conflict's issue names our commit and files and lists the upstream commits that touched them. A cause that stays the same (the same conflict, the same red `main`, the same tag) on a newer upstream only retitles the issue. On a maintainer machine with a notify hook (see [Private hooks](#private-hooks)), the updater reports each issue and cause once.
- A sync that brings upstream changes under `Tinycast/DesignSystem/`, to `Theme.swift` or to `docs/ui.md` opens one `notchcast-design` issue listing those upstream commits. The issue stays open until someone refreshes `notchcast/docs/design-system.md` and closes it.

## Shared repository configuration

`notchcast/config.env` owns the repository names, maintainer identity and tested-status context. Shell scripts source it. Python tools use `ci.config()`. Git URLs and the trusted local-status creator are derived from those values.

`python3 notchcast/check-config.py` compares literal counts in `notchcast/` and explicit lists of fork-owned workflows and GitHub documents with `notchcast/config-literals.json`. Upstream-owned files are never scanned, and the guard runs during build checks, not before replay planning. The checked exceptions are documentation and historical source references, independent test fixtures and workflow comments. `python3 notchcast/check-config.py --list` lists every path and key. A changed literal or an unlisted copy fails. `python3 notchcast/check-config-test.py` demonstrates a deliberately wrong literal failing and the restored literal passing.

Snapshot and Sync both use `notchcast/actions/release` for signing, Release arm64 compilation, signature and identity checks, a 30-second launch check, and zip and dmg packaging. The action receives version, build and signing material explicitly. Identity is checked after signature verification in both workflows. Publication and cleanup remain with each workflow. `bash notchcast/release-test.sh` checks that both workflows call the action once and exercises live and crashed process fixtures. The test uses Ruby's standard-library YAML parser.

## Secrets and checks

- Actions secrets live in the environment `sync`, which only `main` may use: `SIGNING_P12_BASE64` and `SIGNING_P12_PASSWORD` (the self-signed code-signing identity) and `DEPLOY_KEY` (write deploy key `notchcast-actions`; `GITHUB_TOKEN` cannot push commits that touch workflow files). The same material is kept outside git on the maintainer's Mac. The public leaf fingerprint is `RELEASE_SIGN_SHA1` in `config.env`, which only CI's release check reads; each Mac's updater trusts its own `SIGN_SHA1` line in `~/.config/notchcast/private.env` (see [Installing on a Mac](#installing-on-a-mac)).
- `.github/workflows/leaks.yml` and the hooks in `notchcast/githooks` run gitleaks and `check-identity.sh` (no employer name in files, commit messages or commit identities). Per clone, before the first commit: `git config core.hooksPath notchcast/githooks`, a repo-local `user.email` noreply address, and `git remote set-url --push upstream DISABLED`.
- `.claude/settings.json` runs `notchcast/require-draft-pr.py` before every Bash call of a Claude Code session started in this repo: `gh pr create` (or `gh pr new`) without `--draft`, `-d` or `--draft=true` is refused, since a ready PR starts a full PR build. Other agents and a human shell are not covered. `python3 notchcast/require-draft-pr-test.py` feeds it sample commands.
- `.github/workflows/codeql.yml` runs CodeQL (actions, javascript-typescript, python, ruby) on pushes to main, weekly and on dispatch, not on PRs. GitHub's default setup must stay off (`code-scanning/default-setup` `state=not-configured`), or uploads from this workflow are refused.
- Sync commits use `github-actions[bot]`; snapshot annotated tags use the repository identity.
- UI checks: `notchcast/design-check.sh` runs our fork of [enmerasoftware/ai-design-check](https://github.com/enmerasoftware/ai-design-check), [`kaczordodgers/ai-design-check`](https://github.com/kaczordodgers/ai-design-check) (npm spec `DESIGN_CHECK_SPEC` in `config.env`, a pinned tag; Node 20+), which lets commands, buttons and menu items keep Title Case in Swift, on `Tinycast/` with upstream's own findings as the baseline, so only what our commits add counts: errors fail (icon-only buttons without a name, Title Case headings and labels, radii and type off the scale, ...), warnings are shown. It runs in `.github/workflows/design.yml` on pushes and pull requests that change Swift, and in the pre-commit hook when Swift under `Tinycast/` is staged. A deliberate exception gets `// ai-design-check-ignore-next-line <rule> -- <reason>`.

## Private hooks

Maintainer-specific integrations stay out of this repo. `kick.sh`, `update.sh`, `local-ci.sh` and `ready-check.sh` source `~/.config/notchcast/private.env` when it exists; every hook is optional, and a missing one turns its feature off:

- `SIGN_SHA1`: the leaf certificate fingerprint `update.sh` requires of every build it installs. Required, not a hook: without a 40-digit uppercase hex value here `update.sh` installs nothing and logs why. `install-launchd.sh` writes it once when the line is missing, from `RELEASE_SIGN_SHA1` in the commit it installed the tooling from, and never replaces it.

- `notchcast_notify`: a shell function that receives one alert line on stdin (sync trigger failures and open failure issues).
- `notchcast_build_done`: receives the `build/local` result line on stdin when `local-ci.sh` ends.
- `NOTCHCAST_BUILD_QUEUE`: a command that runs `hold [--landing] -- <command>` through a machine-wide build queue (`local-ci.sh`, `ready-check.sh`, and `check-addon-delete.py` from `private.env`, the environment winning for `check-addon-delete.py`; `app-proof.py` from the environment). Without it, builds run directly.
- `NOTCHCAST_LOCAL_CI_DIR`: where `local-ci.sh` keeps its logs (default `~/Library/Caches/notchcast/local-ci`). The build scratch always lives in the per-user temporary directory (`getconf DARWIN_USER_TEMP_DIR`): Debug binaries embed absolute source paths that `-file-prefix-map` does not remap (Swift's escaping-closure check).
- `NOTCHCAST_AGENT_SESSIONS_EXCLUDE`: comma-separated path-component prefixes that Agent Session Logs must never access, matched case-insensitively. The app reads this key as plain `KEY=value` text from `~/.config/notchcast/private.env` on each refresh and never executes the file. A missing file or key excludes nothing; an unreadable or invalid UTF-8 file, more than one line naming the key, or a line that is not one `[export ]KEY=value [# comment]` assignment whose value, bare or in one pair of `"` or `'`, uses only `A-Z a-z 0-9 - _ . ,`, prevents the scan. Any line holding the key's letters in order counts as naming it. The app sees the key only when it is written out literally on one line of this file; a value set by another sourced file or an `eval`, or under a key name the shell builds (a variable, `$'\…'` escapes, `$(…)` or brace ranges), is not seen, so write the key plainly and only here.

## Installing on a Mac

`notchcast/install-launchd.sh all` once per Mac; logs are in `~/Library/Logs/notchcast/`. It:

1. installs the newest snapshot at `/Applications/Notchcast.app` (`update.sh`);
2. copies the old Tinycast Beta data once (`migrate.sh`), each part only while the Notchcast side is still empty: preferences (`defaults export com.tinycast.app.beta | defaults import app.notchcast`), `~/Library/Application Support/com.tinycast.app.beta/` and `~/.config/tinycast-beta/settings.json` (to `~/.config/app.notchcast/`). The old data is never changed. Keychain secrets (keyed by bundle id) are not copied;
3. quits Tinycast Beta and moves its `.app` to the Trash;
4. loads the two LaunchAgents below. It does not start Notchcast and no agent runs it: Notchcast starts at login through its own "Launch at login" setting (Settings → General, `SMAppService`), which needs to be turned on once.
   - `notchcast.kick` runs `kick.sh` every 10 minutes (needs `gh` logged in; `install-launchd.sh kick`): it starts `sync.yml` when upstream `main` or upstream's newest release differs from what it last started for, and at least hourly. While `sync.yml` is disabled (`gh workflow disable Sync`) it logs that and does nothing else: no start, no alert. If a Sync is queued, pending or waiting, it logs a skip (also with `--dry-run`) and leaves trigger state for the next tick to re-evaluate. With a notify hook it reports once when it cannot start the sync, once per upstream commit that waits for the keeper's review (an open `upstream-sync` PR; no lag alert then), and once per upstream commit missing from our `main` 40 minutes after it was committed while no `notchcast-sync` issue is open and the Sync is not holding the rebase for open PRs (`ci.py hold`, within its 12 hours). Like the update job, it runs `kick.sh` from the installed tooling copy, never from the checkout. Log: `~/Library/Logs/notchcast/kick.log`.
   - `notchcast.update` runs `update.sh` every 30 minutes (needs `gh` logged in), unless Notchcast's own "Automatically check for updates" is off (`general.automaticallyCheckForUpdates: false` in `~/.config/app.notchcast/settings.json`; then it logs that and installs nothing): the newest snapshot is installed when its timestamp is newer, the installed version is not a snapshot, or the timestamps match and the installed copy is not ours, after checking bundle id, version and our leaf certificate. A release that failed its check is not installed again until `update.sh --retry`. `install-app.sh` keeps one previous bundle in `~/Library/Application Support/notchcast/previous/`, sending its predecessor to the Trash. If Notchcast was running, it quits it by bundle id (as a user Quit would; one still running after 20 seconds counts as a failure), reopens it in the background with `open -g` and checks that the same pid stays up for 60 seconds, restoring and checking the previous bundle if the new one fails. Failed bundles go to the Trash. If Notchcast was not running, it installs without launching it; every install logs what was left running. `notchcast/update.sh --install` bypasses only that preference, for example to install a build on every maintainer machine at once; combine with `--dry-run` in either order to check without installing. Settings, data and Keychain items are never touched.

The new bundle id and signature need Accessibility to be granted once.

Keep Awake and Keep Awake with Lid Closed were removed (#836). A Mac that installed their root helper keeps it, since the app cannot delete root-owned files; if that helper exists, clean up once by hand in Terminal: `[ -e /Library/PrivilegedHelperTools/app.notchcast.root ] && sudo pmset -a disablesleep 0; sudo rm -f /Library/PrivilegedHelperTools/app.notchcast.root /etc/sudoers.d/notchcast`. The `pmset` step runs only when the helper is there, because another tool may own a lid-closed setting on a Mac that never had it; the `rm` removes the helper and its sudoers rule.

The jobs never fetch or refresh their tooling (#872). Every `install-launchd.sh` mode copies the committed `notchcast/` of the checkout it runs from (its `HEAD`, without uncommitted changes, which it warns about) to `~/Library/Application Support/notchcast/tools`, recording the commit in `tools/.commit`, and the update, sync check and prune jobs run only that copy. Pulling `main` changes nothing they run: to update the tooling on a Mac, run `notchcast/install-launchd.sh update` and `notchcast/install-launchd.sh kick` (and `prune` where it is installed) by hand from an up-to-date checkout. The update and sync check jobs run the copy's real folder, not the `tools` link, so a job still running keeps reading the copy it started from; the installer points both jobs at the new copy, keeps the previous one for such a job, deletes older ones, and refuses a `HEAD` that lacks a file the jobs need. With no installed copy a job exits with an error and never runs the checkout. After a complete copy it also writes the `SIGN_SHA1` pin to `private.env` once, taken from `RELEASE_SIGN_SHA1` in that commit's `config.env` (see [Private hooks](#private-hooks)). A newer snapshot (automatic or `--install`) installs at once, restarting the app only if it was running; there is no idle wait.

## Conflict-free PRs

Merge only with `notchcast/land.sh <pr>`. It checks an isolated merge of the PR head into current main, runs core and affected fork harnesses, and squash-merges only that PR head after they pass. It refuses unless the PR targets `main`, `build` is green on that head, and `design` and `leaks` passed on it when they ran (path filters may skip them). A PR cut before a Sync rewrite merges from its fork point on the replaced main, which Sync keeps under `refs/notchcast/synced/`. It always runs main's copy of `notchcast/`, and it, like the generated-files push, waits while a Sync plan or replay holds the main lease. `notchcast/land.sh <pr> <pr>...` lands a train in one run: each PR passes the same gates on its own head and is merged and squashed onto the one before it (one commit per PR, in the order given); the harnesses any of them selects run once, in one parallel pass, on the final tree; one plain push lands the chain. A PR whose gates or merge refuse is dropped with its reason and the rest goes on. A red pass first reruns the failing harnesses alone on the merged tree; if they pass there, it refuses them as a load-only flake (or a PR that breaks them only under load: land fewer PRs to find it) instead of blaming a PR. Otherwise it reruns only the harnesses still failing on halves of the train to find the first PR that turns them red, drops it, and merges and tests the rest again, so a tree lands only after its own selection passed. When a live green PR build already built and tested exactly the merged tree (its `tested-tree-<tree>` artifact, as Sync's plan uses), the pass runs only the harnesses `CI_SKIP_TESTS` keeps off the runner.

One CI run for a whole train: `notchcast/train.sh <pr> <pr>...` merges each PR head onto current main in order with land.sh's own `merge_onto` (one merge commit per PR, the PR head its second parent), pushes it as `train/<a>-<b>-<c>`, dispatches PR, Proof, Design and Leaks on it with current main as their `base` input (so they check what a PR run checks) and waits. PR and Leaks fail a `train/` run dispatched without `base`, and Main harnesses runs only when dispatched. A green train prints `notchcast/land.sh --train-run <sha> <pr>...`. A red train cancels its other runs, deletes its branch, and is split in halves, each a new train on current main, down to the PR that is red alone; each green part prints its own land line. A split round checks every new branch name and builds every half before it pushes any, and a train.sh that stops early cancels and deletes each train it pushed that has no verdict yet.

`land.sh --train-run <sha> <pr>...` skips each PR's own head checks only when all of these hold, and otherwise says why and lets each PR's own head decide, exactly as without a train:

- `<sha>` has `build`, `design` and `leaks` green, and `proof` too when `app-proof.py plan` selects any;
- its first-parent chain merges each named PR's current head, in the order given;
- its base is current `origin/main`;
- the tree land.sh merges is the tree `<sha>` tested;
- each PR is open, and a draft PR only with the `land` label, the lead's sign-off to land it on the train run (a draft runs no PR build of its own; the train run is that build).

Without `--train-run` a draft is refused as always. Covered by a train, the run is all or nothing: a PR that moves or refuses, a red merged-tree pass (still bisected, still refusing when main is red), or main moving before the push refuses the whole run instead of dropping a PR. Its merged-tree pass runs only the selected harnesses the hosted runner skips (`CI_SKIP_TESTS`), since the train run tested that exact tree. After landing it deletes the train branch.

Main harnesses (`.github/workflows/main-harnesses.yml`) runs only on manual dispatch, so a branch gets its harness verdict, compile errors included, from GitHub with no local build. A newer dispatch on the branch cancels the older run, which notchcast-ci.py then reports as NOPROOF. It has no push trigger: a branch with a ready PR gets its harnesses from the PR workflow alone, never a second time from a push run. A draft PR's branch or one with no PR gets them by `python3 notchcast/notchcast-ci.py --repo .` (below), by `gh workflow run "Main harnesses" --ref <branch>`, or by marking its PR ready. A run that selects no harness skips the shards and concludes success; a branch whose diff `notchcast/lanes.py` says needs no Xcode lane selects none. It does not run on `main`, where Sync's `test_main` runs the full suite on the same commit. Its `plan` job, on Linux, selects the harnesses changed since `notchcast/fork-point.sh origin/main HEAD` (the `Changed harnesses` step prints them) and starts one macOS shard per 40 of them, at most 3; each shard runs its share in one parallel invocation with retries alone and upstream failure comparison, with a 30-minute timeout. This is not an app build: switches in files no selected harness compiles, UI integration, and main moving between the check and the merge remain outside its protection; the PR build is still required.

`python3 notchcast/notchcast-ci.py --repo .` pushes the current branch, dispatches main-harnesses.yml on it, never with more than 3 dispatches outstanding, and waits for the verdict; `python3 notchcast/notchcast-ci-test.py` tests it.

The PR workflow runs its jobs side by side: `checks` (`ci-build.sh`: the script checks, the Debug build, lint), three `harnesses` shards that split the whole suite, `script-tests` on macOS, which runs every script test (`--all`), and `build` on Linux, which is green only when every job the diff needs is and only after `checks` and the shards ran uploads the `tested-tree-<tree>` artifact. `land.sh` reads `build`: the newest `build` run on the PR head decides, but a cancelled or skipped run (a duplicate dispatch the concurrency rule cancelled) counts only when no other run exists, so it never hides a green run and a failed run newer than the green one still refuses; `design`, `leaks` and `proof` are read the same way. The `route` job asks `notchcast/lanes.py` which jobs the diff (against the PR base, `-f base`, else `merge-base origin/main HEAD`) needs: docs (Markdown outside `Tinycast/`, `Tests/`, `.github/`, `notchcast/licenses/`, `notchcast/vendor/` and `NOTICE.md`, and `docs/`) need none, a `notchcast/` file outside `notchcast/actions/` that nothing in the build names (from `ci-build.sh`, `lanes.py`, the `xcode`, `xcodegen` and `tests` actions, or any path outside `notchcast/` and `.github/`, followed transitively) needs only `script-tests`, and every other path, an unknown one, any error and any `v2/addons-*` branch needs all. A job the diff does not need is skipped and still reports; `build` accepts exactly those skips and, without `checks`, runs `check-config.py` itself. The script tests run on macOS because the tools they test do (BSD `sed` and `date`, `swift`, `xcrun`). GitHub runs at most 5 macOS jobs at once for this account, across every branch (measured 2026-11-10 and 2026-11-11: with five running, each further queued job started only when one finished), so one PR run takes all five; a fourth shard would not shorten the run, which `checks` bounds. It does not build draft PRs (converting to draft cancels a running build; `land.sh` refuses a skipped build); mark the PR ready, or dispatch it, to get one.

Shards and the selection are filters on the runner's finished queue in `notchcast/test-harnesses.sh`, so upstream's `Scripts/run-tests.sh` is never patched: `HIDDEN_TESTS` drops hidden features' harnesses from every run, local ones included, and `changed-harnesses.sh` never selects them, `NOTCHCAST_ONLY_TESTS` keeps the named harnesses, `NOTCHCAST_SHARD="<index> <count>"` keeps the harnesses whose name hashes to that index, and `CI_SKIP_TESTS` drops what the hosted runner cannot run, only when `RUNNER_ENVIRONMENT` is `github-hosted`. Every harness is in exactly one shard, and it stays in it when other harnesses are added or removed. A run that names one harness (`run-tests.sh <name>`) bypasses all four.

A `pull_request` run selects its harnesses (`NOTCHCAST_HARNESS_SELECT: on` in `pr.yml`): a sure selection is all it runs, in shard 0 alone (the other shards skip their tests step), and anything else runs the whole suite. `build` reads the same jobs either way. A run of a selection uploads no `tested-tree-<tree>` artifact, because it proved only its selection: `land.sh` then runs its own selection on the merged tree as it does for any tree no PR build proved, and Sync tests the landed `main` whole before a snapshot ships it. A dispatched run (a train) stays in shadow and runs the whole suite, since `land.sh --train-run` takes it as proof of the train's tree. When the build lane runs, `route`'s `Harnesses the diff needs` step runs `notchcast/harness-select.py plan`, which asks `changed-harnesses.sh --unsure <file>` for the harnesses the PR diff selects and the reasons the selection is unsure, and in `on` mode hands a sure selection to the shards as `harness-only` (empty runs the whole suite, so a failed or missing plan does too). Unsure means only the whole suite is safe: the selector, `git diff`, `harness_inputs.py` or `lanes.py` failed; the diff touches what selects or runs harnesses (`changed-harnesses.sh`, `harness_inputs.py`, `command-harness-sources.sh`, `test-harnesses.sh`, `ci-tests.sh`, `config.env`, `lanes.py`, `Scripts/run-tests.sh`, `project.yml`, `notchcast/actions/tests/`, `pr.yml`); the diff touches shared code (`Tinycast/DesignSystem/`, `Tinycast/Platform/`, `Tinycast/Features/Notchcast/Core/`, `Tests/Kit/`), which a harness may reach through a source its header does not list; a path `lanes.py` says the build needs matches no harness file, source pattern, read or kit; or nothing beyond `notchcast-hidden-features-test` is selected. `ci-tests.sh` writes each harness that fails for good (after its lone retry and the upstream comparison) to `$RUNNER_TEMP/harness-failures`, and each shard's `Failures outside the harness selection` step (`harness-select.py misses`) reports a failure a sure selection left out as a miss, with a `::warning::` annotation, which only a shadow run can find; a shard whose tests step did not succeed yet named no harness (the upstream comparison broke, or the suite failed without a `.failed` file) reports `misses=unjudged`. Neither step can fail the run. Every line they print starts with `harness-select`, so `gh run view <run> --log | grep harness-select` shows the plan (`mode=<on|shadow> selected=<n>/<suite> unsure=<reasons|no> runs=<the selection|the whole suite>`) and each shard's `misses=<names|none|unjudged>`. Before selection was switched on (#982), replaying the selector over the four PR runs of 2026-11-15 to 2026-11-18 in which a harness failed found every failed harness inside the selection or the selection unsure. Main harnesses and `land.sh` keep the plain selection, without the unsure rule.

Compiled harnesses are cached (`notchcast/actions/tests`, `actions/cache`). `ci-tests.sh` puts `notchcast/swiftc-cache.py` on `PATH` as `swiftc` when `NOTCHCAST_SWIFTC_CACHE` is set: a compile whose key matches copies the cached binary instead of compiling, and the harness still runs. The key is the compiler version, SDK and OS build, the working directory, every argument except the `-o` path, and the contents of every argument that is a file. A compile with an option outside the script's `PLAIN` list, or a directory argument, is never cached, so add a new harness compiler flag there once it is known to name no unlisted input or second output. Each job restores the newest cache of its own name (`pr-<shard>of<count>`, `push-<shard>of<count>`, `release-<tag>`, or `all` for Sync and Snapshot on `main`), else `main`'s `all`, drops the entries it did not use, and saves a new cache only when it compiled something. GitHub lets a branch or PR read its own caches and `main`'s, never another branch's. `python3 notchcast/swiftc-cache-test.py` covers the key and the pruning with a stand-in compiler.

`notchcast/local-ci.sh <pr>` builds and tests the exact PR head on a maintainer machine, through the build queue when one is configured. Before the build it merges the PR onto main with land.sh's own `merge_onto` (`notchcast/merge.sh`, which both scripts source: fork point after a Sync rewrite, union drivers, both string catalogs, drift gates, sign-off, defect test, typecheck), so whatever land.sh would refuse fails local CI with the same `REFUSED:` message. It posts `build/local` success or failure with the minutes and the last step or the refusal, and keeps the log in `$NOTCHCAST_LOCAL_CI_DIR/logs/<sha>.log`. Success cancels that head's pending PR Actions runs and supplies build proof to `notchcast/land.sh`.

`notchcast/ready-check.sh [base-ref]` (default `origin/main`) first prints `upstream touch: <files> files, +<a> −<d> (base <upstream merge-base>)` (upstream files modified or deleted) and `delta: <files> files, <lines> lines` against the base ref, and fails as `FAIL footprint` when a branch named `v2/addons-*` other than `v2/addons-core` (or `NOTCHCAST_READY_BRANCH`) changes any path that exists on upstream `main`. A branch cut before a Sync rewrite is judged from its fork point (`fork-point.sh` as it is at the base ref, over the fork's `refs/notchcast/synced/*`), printed as `fork point: <sha>, before a Sync rewrite`: the footprint, the private-data checks, `ci-build.sh`'s `BASE_SHA` and the delete test's trigger diff from there, so the rewritten main is not counted as the branch's change; the drift gates and the tools stay at the base ref. It then runs `land.sh`'s drift gates (`drift-gates.sh` and `check-drift.py` from the base ref, the base ref standing in for `origin/main`) and fails as `FAIL drift`. Next it runs `leaks.yml`'s private-data checks, `check-identity.py diff` and `metadata` as they are at the base ref (on the first install, when the base has no scanner, `HEAD`'s, printed as `identity: bootstrap, scanner from HEAD`), then `HEAD`'s too (it can only add failures), against the base ref, with the caller's `PATH` and none of the git or Python environment `HEAD`'s `config.env` sets, and fails as `FAIL identity: <mode> …` with the redacted locations. It guards against accidental leaks, not a hostile committer: `config.env` is still sourced shell, so it can redefine shell functions before the gate runs. Then it runs every gate `pr.yml` runs, in its order, on the committed `HEAD` against that base, with no PR and no GitHub status: it runs `ci-build.sh` unsharded (harnesses included) in a shared clone under the per-user temporary directory, through the build queue when one is configured. On success it prints `retried: <harnesses>` and `ignored (fails upstream too): <harnesses>` (each `none` when empty), the harnesses `ci-tests.sh` passed only on a lone retry or ignored because they fail on upstream too, then one `PASS` line; otherwise `FAIL <step>` with the log's tail; the full log is `~/Library/Caches/notchcast/ready-check/<sha>.log`. It does not merge onto main, which `land.sh` and `local-ci.sh` add. `ready-check-test.py` fails when `pr.yml` or its local actions gain a step the script does not cover.

One landing hold covers every Mac: `notchcast/hold.sh set [--handover] <owner> <minutes>` (owner: a PR number, or a name the lander passes as `NOTCHCAST_LAND_AS`), `hold.sh show`, `hold.sh release`. It is the repository variable `LANDING_HOLD`; until it expires, `land.sh` lands only the owner's PR, checking at its start and again before each push, and refuses when the hold cannot be read. `set` refuses over another owner's unexpired hold unless `--handover`; the same owner may extend. `land.sh <pr>` also takes the hold itself at its start when there is none (value `<pr> <expiry> auto <host>:<pid>`, `NOTCHCAST_LAND_HOLD_MINUTES` long, default 150), so the lander that started first is never refused at the end by a hold set during its harnesses; it refuses at the start under another owner's live hold, takes nothing under its own, renews it for another `NOTCHCAST_LAND_HOLD_MINUTES` before each push while it is still exactly the value it wrote, and at every exit (even after a failed claim) releases the hold only if it is still exactly the value it wrote. A SIGKILL skips that release, so an `auto` hold whose lander ran on this Mac and is no longer running counts as no hold (`hold.sh show` says so); one from another Mac still holds until it expires. A train takes one hold, named for its first PR; under a live hold that names one of its PRs it lands only that PR. Meanwhile the owner's `local-ci.sh` build takes the build queue's landing lane, ahead of every normal job, and any other PR's `local-ci.sh` waits until the hold ends; an `auto` hold does neither, so a landing does not stall other builds.

PRs carry no generated files: edit their inputs, regenerate locally before using Xcode (`xcodegen generate`), and leave the generated diff uncommitted. PR CI regenerates the Xcode project before building, not the Raycast runtime. After each source push to main, the Generated files workflow runs `ci.py regenerate` and commits only `GENERATED` as `Notchcast: generated files` with the repository identity; each attempt starts from a fresh `origin/main`, its generated-only push is excluded by path filters, and the Actions token starts no further workflow runs. If it waits out a Sync replay past its 60 min timeout and that replay fails, main keeps stale generated files until the next source push. Sync regenerates before every build too.

A run also sweeps the throwaway `UserDefaults` suites it left in `~/Library/Preferences` (`notchcast/pref-sweep.py`, hooked from `test-harnesses.sh`): the last run to finish deletes the new plists named like a suite `Tests/` builds (a literal prefix followed by a UUID, or an app domain with "test"), whether the suite passed, failed or was killed, and never a file that existed when the run began or a real app domain. Any other new UUID-named plist is left and printed as `pref-sweep: left <n> unknown`, so a harness shape the prefixes miss shows up instead of being deleted on a guess.

Fork harnesses are discovered by `notchcast/test-harnesses.sh`, so a PR never edits `Scripts/run-tests.sh`. `notchcast/harness_inputs.py` resolves inputs for that runner, `changed-harnesses.sh`, and `check-module-harness.py`. `check-module-harness.py` (the `module-harness` step of `ci-build.sh`) fails when the PR adds a `*Module.swift` that no harness compiles. `Tests/nc-<Folder>-<name>-test.swift` compiles all Model and Service sources of `Tinycast/Features/<Folder>/`. A `// notchcast-sources: <compiler arguments and source globs>` or `// notchcast-kit:` header overrides that folder rule. Other fork harnesses (`Tests/notchcast-*-test.swift` or an upstream-style name) declare their sources in one or more such lines. Paths contain no spaces. For upstream-registered harnesses it also reads the `run` arguments from `Scripts/run-tests.sh`, resolving its variables and continued lines without duplicating those source lists. The resolver includes conditional additions from `command-harness-sources.sh` in one Bash invocation; registration appends only inputs not already supplied by the upstream `run` line. A resolver failure (including malformed headers or a failing conditional helper) emits `::error::` and terminates the runner rather than passing an incomplete suite. A `notchcast-*` harness without the header fails alone with an error; the rest of the suite still runs, and so does a fork-added upstream-style harness (absent from the upstream merge base) that loses its header (a `// notchcast-reads:` line alone does not count). The resolver fetches a missing `upstream/main` ref from `UPSTREAM_REPO` in `config.env` to tell which harnesses are fork-added, and a failed fetch is a resolver error; outside a git repository (a `git archive` copy, as `notchcast-precompile.py` uses) the fork-added check is skipped. A `// notchcast-kit: <name> [<name>...]` header expands to the globs and compiler arguments listed one per line, `#` comments allowed, in `Tests/Kit/<name>.kit`, so harnesses name a shared source set instead of copying its file list (none exist yet); an unknown or empty kit is a resolver error, and changing a kit file selects every harness that uses it.

A `// notchcast-reads: <globs>` header declares repository files a harness reads as text or compiles in a child process. Multiple lines are combined. For example, `// notchcast-reads: notchcast/*.py` makes script changes select the harness without adding them to its compiler arguments. Selection matches the patterns against changed paths, including deleted files. Recursive read sets use `**`, for example `Tinycast/Features/**/*.swift`.

`notchcast/script-tests.py` recursively discovers `notchcast/**/*-test.py`, `*-test.sh`, `*-test.mjs` and `*-test.swift`, including tests directly in `notchcast/`, and runs them with Python, Bash, Node and Swift 6 respectively, one per CPU at a time (`--jobs`), each with its own `TMPDIR`. It prints each test's whole output when that test ends, then a `passed, failed` count, and any failure fails the run. `ci-build.sh` runs it when `pr.yml` does not run it in its own job (local CI, `ready-check.sh`); there `land-test.sh` runs only when the diff against `BASE_SHA` (else `origin/main`) touches a file listed in `notchcast/land-tooling.txt` (`land.sh`, the shell files it sources, and `fork-point.sh`) or itself. `pr.yml` passes `--all`, so every PR build runs every test. `land-test.sh` runs `land.sh --check` on real merged trees and compiles one real harness (`notchcast-hidden-features-test`, the one its fixtures break) per landing; `bash notchcast/land-test.sh --full` runs each fixture's whole selection instead (97 harnesses, twice). `install-app-test.sh` drives `install-app.sh` against synthetic bundles with fake `open`, `osascript` and `launchctl` on `PATH`. Pass `--list` for the default paths or `--all --list` for every discovered path. Run it from the repository root; finding no tests is an error.

Every macOS job runs on GitHub's hosted `xcode-27` image (free on this public repository) except Generated files (`generated.yml`), which runs on `macos-15`, and every other job on `ubuntu-latest`; no workflow names a self-hosted label, so no CI job runs on a maintainer Mac. GitHub runs at most 5 hosted macOS jobs of this repository at once, and the rest queue.

## Drift gates

`python3 notchcast/check-drift.py` checks fork-owned Swift against `notchcast/drift-baseline.json`. It scans production sources under `Tinycast/`. Ownership comes from files added since the merge base of `HEAD` and `upstream/main`, including working-tree additions. The checker fetches the upstream ref from `UPSTREAM_REPO` in `config.env` only when that ref is missing. Upstream-owned Swift is read for references but never gets a gate budget.

The baseline maps each rule to stable keys and integer counts. Each key occupies one line to reduce overlap, but reductions to adjacent keys can still conflict. Keep retired keys at zero instead of deleting them; `--write-baseline` preserves them. A new finding or a higher count fails. A lower count also fails with `lower it in drift-baseline.json`, so removing debt requires lowering its budget in the same change. `--write-baseline` seeds the initial file or tightens existing counts, but refuses growth. `--compare-base <commit>` rejects every added or raised entry, including alert thresholds and zero-valued new keys; a `path` or `path:name` key whose file git pairs as a rename (`-M`) is compared under its old path, while clone and boundary keys are not followed, so a move that changes them still reads as growth. A base without the file permits its first installation.

| Gate | Rule and key |
| --- | --- |
| 1 | Feature-to-feature lexical type references are counted by folder pair. A feature may use its own types, upstream types, `Platform/`, and the reviewed `KERNEL` set in the checker. `NotchcastCore.<member>` lookups outside the kernel are counted per file. Fork files inside upstream feature folders are counted per file. |
| 2 | Production files over 400 lines and fork harnesses over 600 lines are counted by path and exact line count. The planned harness limit is 400 at phase 5. |
| 3 | Types and top-level or static/class members with no production use are counted as `path:symbol`. A name found only in tests gets a separate `test-only` budget. Indented instance functions and properties are skipped to avoid treating SDK callbacks as dead code. Overrides, Objective-C entry points, `@main`, and property wrappers are exempt. The check is lexical, not a compiler reachability proof. Reused names can hide findings. |
| 4 | `npx -y jscpd@$JSCPD_VERSION` checks a temporary copy of fork production Swift for clones of at least 70 tokens and 6 lines between different files. The key is an unordered file pair, and the count is its clone count. The exact jscpd 4 version is pinned in `config.env`. Missing npx, a failed invocation, a 120-second timeout, or a missing or malformed report fails closed. Lowercase literals beginning with `app.notchcast`, `notchcast.`, `com.notchcast`, or the preference-domain prefix `com.apple.` are counted by literal and number of owning folders. Icon names and standard protocol strings are outside that scope. The planned clone threshold is 50 tokens at phase 6. |

A line ending in `// drift: keep <reason>` exempts that line. A file-size exception uses that marker on the final line. Empty reasons do not waive anything. Boundary checks reuse `notchcast/bin/swiftgraph.py` and its literal stripper and file graph. The checker disables Python bytecode writes.

`land.sh` refreshes `upstream/main` before merging so upstream additions are not charged to the fork. It runs the baseline comparison and all four gates on each merged candidate, including retries after main moves. The gate checker and its imported graph code come from the landing base, not the candidate; the first installation uses the invoking checkout when the base has no checker. Tests cannot prove a gate change safe, so a change to `notchcast/check-drift*`, `notchcast/bin/swiftgraph.py`, `notchcast/config.env`, or a file listed in `notchcast/land-tooling.txt` (the same list that triggers `land-test.sh`) is a visible sign-off: landing refuses unless the PR body has a line `Drift tooling: <reason>`, and that line is kept in the squash commit. For the drift tooling itself, the landing base's `check-drift-test.py` also runs against the merged tree with `python3 -I`, as a sanity check only, and a PR that deletes that file is refused. A budget increase refuses with `REFUSED: drift baseline grew`. Other drift failures re-run the checker on the base, print `main is already red` when that also fails, and refuse with `REFUSED: drift` either way. The pre-push hook runs gates 1 to 3 without npx and warns rather than blocking. `land.sh` and `local-ci.sh` share these gates through `drift-gates.sh`; they run locally, not in `ci-build.sh` or an Actions workflow.

A PR whose title starts with `Fix ` after removing an optional `Notchcast: ` prefix, case-insensitively, must add or change a `Tests/*-test.swift` or `notchcast/**/*-test.*` file. Otherwise landing refuses unless the PR body has a line `No test: <reason>` with a nonempty reason. That line is retained in the squash commit. This is the cheap presence check only. It does not prove that the changed test failed on the base commit.

A run of all four gates, which is what `land.sh` and `local-ci.sh` do, ends with the counters (each rule's total against its baseline total, and the pattern counters `try?`, `Task.sleep`, `Process()`, `tool-paths` and `cancellation-loops` in fork production Swift), so the log shows how close each limit is. Each key above its limit prints one machine-readable line, `GATE-THRESHOLD <rule>:<key> <value> <limit>`, such as `dead:<path>:<symbol>` or `clones:<path>|<path>`; a pattern counter prints `GATE-THRESHOLD <counter> <value> <limit>` against its threshold in the baseline's `alerts` map. A pattern crossing whose value does not exceed what the merge base with `origin/main` already had ends with `known`, so only lines without it are new. A new or grown one fails the run with `threshold breach new or grown: <counter> <value> > <limit> (main: <value or none>)`, so `land.sh` refuses it; when `origin/main` counters cannot be read, a `WARN` replaces the failure. The pre-push subset (gates 1 to 3) prints none of this. A reviewer gets only the goal and the diff ([docs/review.md](docs/review.md)).

Nothing runs after landing: a check that only reports or files a task does not exist; it blocks before the merge or it is removed. The retired report counters (`file-lines`, `test-lines`, `waivers`, `upstream-patch-lines`, `fix-no-test`) still sit in `alerts` only because the v2 base checker requires them; the current checker ignores them.

`python3 notchcast/check-drift-test.py` plants boundary lookups, oversized files, dead and test-only declarations, generated clone blocks including one at exactly the jscpd limits (70 tokens, 6 lines), and copied fork/preference literals. Each deliberate violation must exit 1 at its gate. It also checks waivers, SF Symbol exemptions, fail-closed clone checking, baseline tightening, and new, grown and known pattern-counter breaches. `python3 notchcast/land-drift-test.py` exercises the actual landing budget comparison, defect-test presence rule, `Drift tooling:` sign-off, base-fixture run, and a refused pattern-counter breach. The older merged-tree harness fixtures isolate these gates because the drift fixtures test them separately.

## Snapshot releases

`.github/workflows/snapshot.yml` starts primarily on pushes to main, with a cron backstop at minutes 7, 27 and 47, and by manual dispatch. Workflow-level concurrency holds the `snapshot` group through planning, building and publishing; `cancel-in-progress` is true only for a push, so a newer main supersedes the run in flight while cron and dispatch runs queue behind it. Automatic runs plan at once: unchanged main skips, otherwise the tag's timestamp is the later of now and 50 minutes after the latest snapshot's publication (its release's `published_at`, when it reached the Macs), so two publications are always at least 50 minutes apart. The macOS build of that pinned main starts straight away, while the `gate` job waits on Ubuntu until the tag's timestamp; publish needs both, then refetches main and releases and skips with a notice when main has moved, or fails when the latest other snapshot was published under 50 minutes ago. A run cancelled while publishing deletes its draft release and its tag, unless a published release already uses that tag. Manual dispatch never waits in the planner: unchanged main fails with an error; a closed gate exits successfully with a notice including its UTC opening time. A dispatch can still be cancelled while pending when a newer run replaces it: it ends grey "cancelled", never green, and the replacing run builds current main. Sync's deploy-key and land.sh's authenticated pushes trigger Snapshot; Generated uses GITHUB_TOKEN, so its pushes rely on the backstop. A build that finishes before its gate opens publishes when the gate opens, subject to GitHub scheduling. Failed attempts do not block retries. Snapshot planning tests run only in this workflow, before planning.

To publish a waited-for fix early, first cancel any Snapshot run still building or waiting in `gate` (it holds the `snapshot` group; cancelling it before `publish` publishes nothing): `gh run list -R kaczordodgers/notchcast -w Snapshot -s in_progress`, then `gh run cancel <id> -R kaczordodgers/notchcast`; then `gh workflow run Snapshot -f skip_gate=true -R kaczordodgers/notchcast`. It bypasses only the 50-minute gate, retaining unchanged-main protection and every test, lint, signature, identity and launch check.

Generated files retries runner allocation at most twice when its sole `regenerate` job was cancelled before any step started and has GitHub's hosted-runner not-acquired annotation; script failures and exhausted allocation failures remain red.

The workflow regenerates the project and uses sync's `notchcast/actions/tests` action on the captured main commit, including hosted-runner exclusions, retries and comparison against pristine `merge-base(main, upstream/main)`; it skips that action when the main commit already has a green `TESTED_CONTEXT` status from Sync. Lint must also pass. Either failing fails the snapshot without publication; Leaks is independent. Tests and lint run in the `checks` job beside the signed `snapshot` build, and `publish` needs both green. The build uses sync's Release arm64 build, signing identity, signature checks and zip/dmg packaging steps. Build or signing failures publish nothing. Snapshot tags point to that exact main commit and use the repository identity.

Tags append `.snapshot.YYYYMMDDHHMMSS` (UTC) to the newest published upstream mirror version, for example `v0.12.7-beta.131.snapshot.20261104120000`. The app version and asset names include the suffix. The updater selects only non-draft releases whose tags end in `.snapshot.` followed by exactly 14 digits, ordered by that timestamp alone. It ignores upstream mirror, beta and stable releases, regardless of their version or publication time. An installed non-snapshot version is replaced by the newest snapshot. An installed snapshot with a later timestamp is kept, and one with the same timestamp is kept when signed by us. Sync's mirror parser ignores snapshot tags. Existing updater copies must be refreshed to use timestamp-only ordering. Updater selection checks run with `bash notchcast/update-install-test.sh`. Snapshot planning checks run with `python3 notchcast/snapshot-test.py`.

Enable independent 30-minute installs on an installed Mac from its checkout with `/bin/bash notchcast/install-launchd.sh update --auto-install`. This reloads only `notchcast.update`, with `update.sh --install` in its arguments, and runs at load and every 1800 seconds. It never changes `general.automaticallyCheckForUpdates`. Run `install-launchd.sh update` to restore preference-respecting behavior. First-time setup can use `install-launchd.sh all --auto-install`.

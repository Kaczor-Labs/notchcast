# Notchcast maintainer guide

**Notchcast** is a modified fork of [Tinycast](https://github.com/abue-ammar/tinycast) (AGPL-3.0; a modified version, as its section 5a requires us to state): upstream `main` plus a few commits of ours on top, arm64 builds signed with our own identity. Upstream's README is at [abue-ammar/tinycast](https://github.com/abue-ammar/tinycast#readme).

Every ~10 minutes a GitHub Actions workflow checks upstream `main`; once the keeper's review of the new upstream diff passes, it replays our commits onto it, builds and runs the tests, and moves `main` only when green; each upstream release is rebuilt the same way and published here under the same tag.

This file is `notchcast/README.md`, the maintainer guide. The public root `README.md` is generated from `notchcast/README.public.md`; its feature list sits between the `features:start` and `features:end` markers. `main` is the default branch. Feature work happens on branches off `main` and lands as linear commits (no merge commits). Upstream's Raycast extensions stay hidden ([docs/hidden.md](docs/hidden.md)).

Our commits:

- `Notchcast: read releases from kaczordodgers/notchcast`: the in-app updater reads this repo's releases.
- `Notchcast: remove upstream workflows`: none of upstream's workflows run here. The sync makes this commit afresh on every replay, so upstream workflow edits never conflict and new ones never land.
- `Notchcast: tooling` and later fixes: this folder and `.github/workflows/`.
- `Notchcast: bundle id app.notchcast, URL scheme notchcast, name Notchcast`: our own app identity (Debug: `app.notchcast.dev`, name Notchcast Dev; a per-task test copy is named from its bundle id, [fork-strings.md](docs/fork-strings.md#channel-name)). The in-app updater treats it as a development build and stays inert; `notchcast.update` installs releases.
- `Notchcast: generated files`, always last: the root `README.md` (from `notchcast/README.public.md`), `Tinycast.xcodeproj` (XcodeGen from `project.yml`); `Tinycast/Resources/RaycastRuntime.generated.js` counts as generated too but stays upstream's, since Extensions are hidden (`docs/hidden.md#harnesses`). The sync makes it afresh; our other commits never carry these files (replay drops them from each commit), so upstream edits to them never conflict. It also removes every path in `notchcast/prune-paths.txt` (upstream files the app does not need, e.g. `website/`), so upstream edits to them never conflict either. Edit `notchcast/README.public.md` or `project.yml`, never the generated files.

## Sync (`.github/workflows/sync.yml`)

- Upstream review gate (#871): `main` moves onto a new upstream commit U only after an agent review of the upstream diff `old..U` passed. The record is a commit status `REVIEW_CONTEXT` (`config.env`, `notchcast/upstream-review`) on U in this repository; only a status created by the repository owner's account counts (`ci.py upstream_review`), so no workflow token, the Actions bot included, can pass the gate, and the newest owner status wins. The plan job reads it before any job runs upstream's tree; without a success, `main` stays where it is and the run logs why. The main job reads it again right before it pushes `main` (`ci.py reviewed`) and pushes nothing unless it is still a success. Meanwhile the `stage` job (Linux, deploy key, no upstream code run) force-pushes the diff to `sync/upstream` on top of `sync/upstream-base` (the old upstream commit, both without `.github/workflows`, so no push or PR event runs any workflow and nothing reaches a Mac runner) and keeps one draft PR labelled `REVIEW_LABEL` (`upstream-sync`) between them, whose body holds the range, the commits, the diff stat and the exact `gh api` command that records the verdict. A newer upstream updates the same PR; once `main` holds its upstream, the next run closes it. The PR is never merged.
- Who reviews: the Notchcast keeper, on each new `upstream-sync` PR, runs `gate.py pick notchcast review --from sync/upstream` (the gate) and `gate.py pick notchcast review-kimi --from sync/upstream` (a second voice that does not block), each with [review/upstream-review.md](review/upstream-review.md), then records the gate's verdict from their own `gh` login: `gh api -X POST repos/<FORK_REPO>/statuses/<U> -f context=notchcast/upstream-review -f state=success|failure -f description='<verdict>'`. Reviewers never set it themselves. A release tagged on another upstream commit waits (plan logs a notice) until that commit gets its own review and status the same way. With a notify hook, `notchcast.kick` reports once per upstream commit that waits for this review.
- Rebase waits while a non-draft PR from this repo into `main` is open, for at most 12 hours from the oldest upstream commit not in `main`, then proceeds with a warning.
- A replay whose `main` lease is lost because `main` moved meanwhile (a landing or the generated-files push) ends green with a notice; the next Sync (that push, or kick within the hour) replays again.
- Started by `notchcast.kick` (below) when upstream `main` or its newest release changed, at least hourly, on a push to `main` except generated-only changes (`Tinycast.xcodeproj/project.pbxproj`, `Tinycast.xcodeproj/xcshareddata/xcschemes/Tinycast.xcscheme`, `Tinycast/Resources/RaycastRuntime.generated.js`, `README.md`), and by hand. GitHub's own `schedule` stays in the workflow but has never fired for this fork. Each run: if upstream `main` moved and its review passed, the plan job first replays our commits on Linux; a conflict is reported there without spending a macOS runner. Then the `replay` job, which holds no secret and no write token, reads the review again, has `notchcast/ci.py replay` cherry-pick our commits (`merge-base(main, upstream/main)..main`) onto the new upstream `main`, reports the replayed commit and uploads it as a git bundle before any of the tree's code runs, then builds Debug on a GitHub-hosted `xcode-27` runner and runs upstream's `Scripts/run-tests.sh`. Only when green does the `replay push` job (Linux, environment `sync`, none of the tree's code) fetch exactly that commit from the bundle, read the review a third time, take the deploy key and update `main` with `--force-with-lease` on the `main` it started from; `sync-wait.sh` holds landings until it ends. That workflow push and the review branches above are the only history rewrites allowed in this repo; nobody force-pushes by hand. A `main` commit without a green `notchcast/tested` status (a push) is built and tested as it is, and gets that status when green; unless a green PR build of this repository already built and tested its tree: after a green build the PR workflow uploads a `tested-tree-<tree>` artifact (the tree of the checked-out commit without the project, scheme and `README.md`, which CI regenerates or never tests; the Raycast runtime stays in, `ci.py tested-key`), and plan marks `main` tested from a live one whose run is a green `pr.yml` run of `FORK_REPO` (fork PRs never count) and closes the `notchcast-main` issue. Any miss or API error tests `main` as before.
- Every upstream release from `BASELINE_TAG` (`config.env`) on, whose tagged commit was reviewed whole (it is exactly the upstream commit `main` is built on, or carries the owner's own success `REVIEW_CONTEXT` status), is rebuilt from its tagged commit with our commits replayed onto it, tested, built Release for arm64, signed with `Notchcast Self-Signed` and published under the same tag, title and prerelease flag as `Notchcast-<version>.zip` and `.dmg`. Version and build number come from upstream's own zip; mirror versions stay unchanged; snapshots append a numeric revision. A tag on a mere ancestor of a reviewed U waits for its own review: U may delete what that commit added, so the review of `old..U` never showed it. Each release is one call of `sync-release.yml`: `build` (no secret) replays onto the tagged commit, tests, builds and launches it; `sign` (environment `sync`) signs that app and runs none of the tree's code; `publish` tags the replayed commit `build` reported, fetched from its bundle, and creates the release. Plan pins the tagged commit; `build` builds that commit and fails if upstream moved the tag since (`ci.py pin-tag`). For a tag on any commit other than the one `main` is built on, `build` reads that commit's review again before it replays anything and `publish` before it takes the deploy key (`ci.py reviewed`); each fails unless the owner's newest status is still a success. The tag here names the replayed commit that was built, never upstream's tag object, so pushing it starts none of upstream's workflows.
- Tests: upstream's full suite except `HIDDEN_TESTS` (`config.env`), the harnesses of features Notchcast hides (`docs/hidden.md#harnesses`), and, on GitHub-hosted runners only, `CI_SKIP_TESTS` (`config.env`), harnesses the hosted VM cannot run (Vision OCR, rendered-text capture), which must still pass on a Mac. A harness that fails is run once more alone; if it still fails, it is run on the pristine upstream commit under our commits, and only a harness that passes there blocks (a failure on upstream too is upstream's flake or the VM, and is ignored with a warning).
- On a replay conflict, a red build or a red test nothing is pushed or published and `main` stays as it is. Land a hand resolution as `notchcast/replay-fixes/<name>.patch` (full diffs covering exactly the conflicting non-catalog, non-generated files, from the replay's current tip to resolved content; clean cherry-pick results are preserved; lowercase subject with non-alphanumeric runs replaced by hyphens, trimmed at both ends); delete it once Sync has rewritten main. When an older release tag needs a different resolution, add it as `<name>.<base label>.patch` (e.g. `<name>.v0-12-9-beta-134.patch`): the replay tries `<name>.patch` first, then the labelled ones in name order, and uses the first that applies; delete a labelled one once its release is published. A commit that still cherry-picks cleanly but breaks on the new upstream without a conflict (an upstream switch over our settings keys, a source an upstream file now needs) gets an adaptation instead: `notchcast/replay-adaptations/<name>.patch`, named the same way (labelled ones too), applied after that commit is picked, cleanly or by its replay fix; the first that applies is used, and one already in the commit counts as applied unless a copy of a hunk's old lines still remains in the file. The replay fails on that commit when such a copy remains, even where the file repeats those lines on purpose (accepted: the replay cannot tell which copy was meant, so quote enough context to make the hunk unique), and when an adaptation's quoted lines match nowhere, so it applies neither way, as once upstream edits a line it quotes; delete it once Sync has rewritten main. A red build or test is remembered as `refs/notchcast-failed/<main-<upstream>|release-<tag>|test>-<main>`, so it is retried only when upstream or `main` changes; a conflict is found again cheaply on Linux each run.
- Each failure opens or updates one issue per kind, closed by the next green run of that kind: `notchcast-sync` (replaying onto new upstream), `notchcast-main` (a pushed `main` tested as it is), `notchcast-release` (per tag). A conflict's issue names our commit and files and lists the upstream commits that touched them. A cause that stays the same (the same conflict, the same red `main`, the same tag) on a newer upstream only retitles the issue. On a maintainer machine with a notify hook (see [Private hooks](#private-hooks)), the updater reports each issue and cause once.
- A sync that brings upstream changes under `Tinycast/DesignSystem/`, to `Theme.swift` or to `docs/ui.md` opens one `notchcast-design` issue listing those upstream commits. The issue stays open until someone refreshes `notchcast/docs/design-system.md` and closes it.

## Shared repository configuration

`notchcast/config.env` owns the repository names, maintainer identity and tested-status context. Shell scripts source it. Python tools use `ci.config()`. Git URLs and the trusted local-status creator are derived from those values.

`python3 notchcast/check-config.py` compares literal counts in `notchcast/` and explicit lists of fork-owned workflows and GitHub documents with `notchcast/config-literals.json`. Upstream-owned files are never scanned, and the guard runs during build checks, not before replay planning. The checked exceptions are documentation and historical source references, independent test fixtures and workflow comments. `python3 notchcast/check-config.py --list` lists every path and key. A changed literal or an unlisted copy fails. `python3 notchcast/check-config-test.py` demonstrates a deliberately wrong literal failing and the restored literal passing.

Snapshot and Sync both build with `notchcast/actions/release` in a job without secrets (ad-hoc signed Release arm64 compilation, upstream's signature checks, identity check, a 30-second launch check, the app packed for the next job) and sign with `notchcast/actions/sign` in a job that holds the certificate and runs none of the tree's code: `notchcast/sign-app.sh` signs every nested code item inside out, keeping its identifier and entitlements and adding the hardened runtime, with the identity from a temporary keychain that is deleted when the step ends; then `codesign -R` checks the leaf against `RELEASE_SIGN_SHA1` and the action packages the zip and dmg. Publication and cleanup remain with each workflow. `bash notchcast/release-test.sh` checks that both workflows use each action once, that no job that can read a secret or uses an environment runs the tree's code, and exercises live and crashed process fixtures; `notchcast/sign-app-test.sh` signs a fixture app with a throwaway identity. The test uses Ruby's standard-library YAML parser.

## Secrets and checks

- Actions secrets live in the environment `sync`, which only `main` may use: `SIGNING_P12_BASE64` and `SIGNING_P12_PASSWORD` (the self-signed code-signing identity) and `DEPLOY_KEY` (write deploy key `notchcast-actions`; `GITHUB_TOKEN` cannot push commits that touch workflow files). The same material is kept outside git on the maintainer's Mac. No job that can read them runs code from the checked-out tree (#873): builds and tests run in jobs without secrets, and the jobs that sign or push take only the built app or a git bundle whose commit the building job reported before any of the tree's code ran. Every third-party action is pinned to a commit SHA. The deploy-key action trusts only GitHub's published ed25519 host key, and every job that takes the key deletes it in an `if: always()` step. The public leaf fingerprint is `RELEASE_SIGN_SHA1` in `config.env`, which only CI's release check reads; each Mac's updater trusts its own `SIGN_SHA1` line in `~/.config/notchcast/private.env` (see [Installing on a Mac](#installing-on-a-mac)).
- `.github/workflows/leaks.yml` and the hooks in `notchcast/githooks` run gitleaks and `check-identity.sh` (no employer name in files, commit messages or commit identities). Per clone, before the first commit: `git config core.hooksPath notchcast/githooks`, a repo-local `user.email` noreply address, and `git remote set-url --push upstream DISABLED`. Its `post-checkout` hook then registers the `notchcast-words` merge driver `.gitattributes` names, on every checkout and every new worktree, so a plain `git merge` in any copy merges those lists by word; `notchcast/merge-rules-test.sh` proves it on a fresh worktree.
- `.claude/settings.json` runs `notchcast/require-draft-pr.py` before every Bash call of a Claude Code session started in this repo: `gh pr create` (or `gh pr new`) without `--draft`, `-d` or `--draft=true` is refused, since a ready PR starts a full PR build. Other agents and a human shell are not covered. `python3 notchcast/require-draft-pr-test.py` feeds it sample commands.
- `.github/workflows/codeql.yml` runs CodeQL (actions, javascript-typescript, python, ruby) on pushes to main, weekly and on dispatch, not on PRs; it skips the hidden Raycast runtime (`docs/hidden.md#harnesses`). GitHub's default setup must stay off (`code-scanning/default-setup` `state=not-configured`), or uploads from this workflow are refused.
- Sync commits use `github-actions[bot]`; snapshot annotated tags use the repository identity.
- UI checks: `notchcast/design-check.sh` runs our fork of [enmerasoftware/ai-design-check](https://github.com/enmerasoftware/ai-design-check), [`kaczordodgers/ai-design-check`](https://github.com/kaczordodgers/ai-design-check) (`DESIGN_CHECK_SPEC` in `config.env`: the tarball of one commit, which it has no dependencies to vary; Node 20+), which lets commands, buttons and menu items keep Title Case in Swift, on `Tinycast/` with upstream's own findings as the baseline, so only what our commits add counts: errors fail (icon-only buttons without a name, Title Case headings and labels, radii and type off the scale, ...), warnings are shown. It runs in `.github/workflows/design.yml` on pushes and pull requests that change Swift, and in the pre-commit hook when Swift under `Tinycast/` is staged. A deliberate exception gets `// ai-design-check-ignore-next-line <rule> -- <reason>`.

## Private hooks

Maintainer-specific integrations stay out of this repo. `kick.sh`, `update.sh`, `local-ci.sh`, `ready-check.sh` and `land.sh` source `~/.config/notchcast/private.env` when it exists; every hook is optional, and a missing one turns its feature off:

- `SIGN_SHA1`: the leaf certificate fingerprint `update.sh` requires of every build it installs. Required, not a hook: without a 40-digit uppercase hex value here `update.sh` installs nothing and logs why. `install-launchd.sh` writes it once when the line is missing, from `RELEASE_SIGN_SHA1` in the commit it installed the tooling from, and never replaces it.

- `notchcast_notify`: a shell function that receives one alert line on stdin (sync trigger failures, open failure issues, and what `land.sh --guard` found red on macOS after a Linux landing).
- `notchcast_mac_route`: a shell function that receives the PR numbers of a landing `land.sh` started on Linux and that needs a Mac, and hands it to one, where `notchcast/land.sh <pr>...` lands it. Without it `land.sh` prints that command.
- `notchcast_build_done`: receives the `build/local` result line on stdin when `local-ci.sh` ends.
- `NOTCHCAST_BUILD_QUEUE`: a command that runs `hold [--landing] -- <command>` through a machine-wide build queue (`local-ci.sh`, `ready-check.sh`, and `check-addon-delete.py` from `private.env`, the environment winning for `check-addon-delete.py`; `app-proof.py` from the environment). Without it, builds run directly.
- `NOTCHCAST_LOCAL_CI_DIR`: where `local-ci.sh` keeps its logs (default `~/Library/Caches/notchcast/local-ci`). The build scratch always lives in the per-user temporary directory (`getconf DARWIN_USER_TEMP_DIR`): Debug binaries embed absolute source paths that `-file-prefix-map` does not remap (Swift's escaping-closure check).
- `NOTCHCAST_AGENT_SESSIONS_EXCLUDE`: comma-separated path-component prefixes that Agent Session Logs must never access, matched case-insensitively. The app reads this key as plain `KEY=value` text from `~/.config/notchcast/private.env` on each refresh and never executes the file. A missing file or key excludes nothing; an unreadable or invalid UTF-8 file, more than one line naming the key, or a line that is not one `[export ]KEY=value [# comment]` assignment whose value, bare or in one pair of `"` or `'`, uses only `A-Z a-z 0-9 - _ . ,`, prevents the scan. Any line holding the key's letters in order counts as naming it. The app sees the key only when it is written out literally on one line of this file; a value set by another sourced file or an `eval`, or under a key name the shell builds (a variable, `$'\…'` escapes, `$(…)` or brace ranges), is not seen, so write the key plainly and only here.

## Installing on a Mac

`notchcast/install-launchd.sh all` once per Mac; logs are in `~/Library/Logs/notchcast/`. It:

1. installs the newest snapshot at `/Applications/Notchcast.app` (`update.sh`);
2. copies the old Tinycast Beta data once (`migrate.sh`), each part only while the Notchcast side is still empty: preferences (`defaults export com.tinycast.app.beta | defaults import app.notchcast`), `~/Library/Application Support/com.tinycast.app.beta/` and `~/.config/tinycast-beta/settings.json` (to `~/.config/app.notchcast/`). The old data is never changed. Keychain secrets (keyed by bundle id) are not copied;
3. quits Tinycast Beta and moves its `.app` to the Trash;
4. loads the two LaunchAgents below. It does not start Notchcast and no agent runs it: Notchcast starts at login through its own "Launch at login" setting (Settings → General, `SMAppService`), which needs to be turned on once.
   - `notchcast.kick` runs `kick.sh` every 10 minutes (needs `gh` logged in; `install-launchd.sh kick`): it starts `sync.yml` when upstream `main` or upstream's newest release differs from what it last started for, and at least hourly. While `sync.yml` is disabled (`gh workflow disable Sync`) it logs that and does nothing else: no start, no alert. If a Sync is queued, pending or waiting, it logs a skip (also with `--dry-run`) and leaves trigger state for the next tick to re-evaluate. With a notify hook it reports once when it cannot start the sync, once per upstream commit that waits for the keeper's review (an open `upstream-sync` PR; no lag alert then), and once per upstream commit missing from our `main` 40 minutes after it was committed while no `notchcast-sync` issue is open and the Sync is not holding the rebase for open PRs (`ci.py hold`, within its 12 hours). Like the update job, it runs `kick.sh` from the installed tooling copy, never from the checkout. Log: `~/Library/Logs/notchcast/kick.log`.
   - `notchcast.update` runs `update.sh` every 30 minutes (needs `gh` logged in), unless Notchcast's own "Automatically check for updates" is off (`general.automaticallyCheckForUpdates: false` in `~/.config/app.notchcast/settings.json`; then it logs that and installs nothing): the newest snapshot is installed when its timestamp is newer, the installed version is not a snapshot, or the timestamps match and the installed copy is not ours, after checking bundle id, version, and the seal and our leaf certificate in one `codesign --verify --deep --strict -R` call. A release that failed its check is not installed again until `update.sh --retry`. `install-app.sh` keeps one previous bundle in `~/Library/Application Support/notchcast/previous/`, sending its predecessor to the Trash. If Notchcast was running, it quits it by bundle id (as a user Quit would; one still running after 20 seconds counts as a failure), reopens it in the background with `open -g` and checks that the same pid stays up for 60 seconds, restoring and checking the previous bundle if the new one fails. Failed bundles go to the Trash. If Notchcast was not running, it installs without launching it; every install logs what was left running. `notchcast/update.sh --install` bypasses only that preference, for example to install a build on every maintainer machine at once; combine with `--dry-run` in either order to check without installing. Settings, data and Keychain items are never touched.

The new bundle id and signature need Accessibility to be granted once.

Keep Awake and Keep Awake with Lid Closed were removed (#836). A Mac that installed their root helper keeps it, since the app cannot delete root-owned files; if that helper exists, clean up once by hand in Terminal: `[ -e /Library/PrivilegedHelperTools/app.notchcast.root ] && sudo pmset -a disablesleep 0; sudo rm -f /Library/PrivilegedHelperTools/app.notchcast.root /etc/sudoers.d/notchcast`. The `pmset` step runs only when the helper is there, because another tool may own a lid-closed setting on a Mac that never had it; the `rm` removes the helper and its sudoers rule.

The jobs never fetch or refresh their tooling (#872). Every `install-launchd.sh` mode copies the committed `notchcast/` of the checkout it runs from (its `HEAD`, without uncommitted changes, which it warns about) to `~/Library/Application Support/notchcast/tools`, recording the commit in `tools/.commit`, and the update, sync check and prune jobs run only that copy. Pulling `main` changes nothing they run: to update the tooling on a Mac, run `notchcast/install-launchd.sh update` and `notchcast/install-launchd.sh kick` (and `prune` where it is installed) by hand from an up-to-date checkout. The update and sync check jobs run the copy's real folder, not the `tools` link, so a job still running keeps reading the copy it started from; the installer points both jobs at the new copy, keeps the previous one for such a job, deletes older ones, and refuses a `HEAD` that lacks a file the jobs need. With no installed copy a job exits with an error and never runs the checkout. After a complete copy it also writes the `SIGN_SHA1` pin to `private.env` once, taken from `RELEASE_SIGN_SHA1` in that commit's `config.env` (see [Private hooks](#private-hooks)). A newer snapshot (automatic or `--install`) installs at once, restarting the app only if it was running; there is no idle wait.

## Conflict-free PRs

Merge only with `notchcast/land.sh <pr>`. It checks an isolated merge of the PR head into current main, runs core and affected fork harnesses, and squash-merges only that PR head after they pass. It refuses unless the PR targets `main`, `build` is green on that head, and `design` and `leaks` passed on it when they ran (path filters may skip them). A PR cut before a Sync rewrite merges from its fork point on the replaced main, which Sync keeps under `refs/notchcast/synced/`. It always runs main's copy of `notchcast/`, and it, like the generated-files push, waits while a Sync plan or replay holds the main lease. `notchcast/land.sh <pr> <pr>...` lands a train in one run: each PR passes the same gates on its own head and is merged and squashed onto the one before it (one commit per PR, in the order given); the harnesses any of them selects run once, in one parallel pass, on the final tree; one plain push lands the chain. A PR whose gates or merge refuse is dropped with its reason and the rest goes on. A red pass first reruns the failing harnesses alone on the merged tree; if they pass there, it refuses them as a load-only flake (or a PR that breaks them only under load: land fewer PRs to find it) instead of blaming a PR. Otherwise it reruns only the harnesses still failing on halves of the train to find the first PR that turns them red, drops it, and merges and tests the rest again, so a tree lands only after its own selection passed. When a live green PR build already built and tested exactly the merged tree (its `tested-tree-<tree>` artifact, as Sync's plan uses), the pass runs only the harnesses `CI_SKIP_TESTS` keeps off the runner.

One CI run for a whole train: `notchcast/train.sh <pr> <pr>...` merges each PR head onto current main in order with land.sh's own `merge_onto` (one merge commit per PR, the PR head its second parent), pushes it as `train/<a>-<b>-<c>`, dispatches PR, Proof, Design and Leaks on it with current main as their `base` input (so they check what a PR run checks), PR with `hosted=true` so a self-hosted Mac, which proves no tree, never runs it and waits. PR and Leaks fail a `train/` run dispatched without `base`, and Main harnesses runs only when dispatched. A PR whose merge onto the train refuses is dropped with a `DROPPED #<pr>` line and a PR comment saying why, and the rest goes on: a conflict names the earlier PR of the train that touched the file (`conflicts with #<x> in the landing batch; rebase on main`), or main. Files marked `merge=notchcast-words` in `.gitattributes` (lists kept on one line) are merged word by word by `notchcast/merge-words.py`, so two PRs that each add a name to the same line both fit, while a word both changed, or one removed beside the other's addition, conflicts as any line does. A green train prints `notchcast/land.sh --train-run <sha> <pr>...`. A red train cancels its other runs, deletes its branch, and is split in halves, each a new train on current main, down to the PR that is red alone, which gets a PR comment with the red run's link and a `CULPRIT #<pr> <run url>` line; each green part prints its own land line. A split round builds every half and checks every new branch name before it pushes any, and a train.sh that stops early cancels and deletes each train it pushed that has no verdict yet. Before anything is pushed or dispatched it refuses a train in which one PR's head holds commits of another's own first-parent line (landing squashes each PR, so the holder can conflict with main once the other lands), naming both: land the one first, then merge main into the holder. Two PRs that merged the same third branch hold nothing of each other. Each round opens with `open PRs: <n>/25`, the open-PR count against the cap. It exits 0 only when every PR it was given came out green.

The landing queue: `notchcast/train.sh --queue` picks the train itself and lands it with no manual step. It takes the first `LAND_BATCH_SIZE` (`config.env`) open PRs against `main`, oldest sign-off first, that are signed off (ready, or a draft with the `land` label; the time is the last ready or label event, or the PR's creation) and have `build` green on their own head (a labelled draft may have no build: the train run is its build). Each green train is landed at once by `land.sh --train-run`, so main fast-forwards to one squash commit per PR and each PR is closed with its commit. After a split, the first green half lands; a later half that was green on the main it left is run again on the new main, and red halves are split onto it, until every PR has landed or is the culprit. A PR whose head holds commits of another in the batch is left out with a `DROPPED #<pr>` line and a PR comment saying so, posted once per head, and the rest goes on. A culprit is not picked again until its head moves (its comment names the head), and a train land.sh refuses keeps its branch and prints `NOT LANDED`. Run one queue at a time, on a Mac when the batch may select a harness in `CI_SKIP_TESTS`, which land.sh still runs itself.

`land.sh --train-run <sha> <pr>...` skips each PR's own head checks only when all of these hold, and otherwise says why and lets each PR's own head decide, exactly as without a train:

- `<sha>` has `build`, `design` and `leaks` green, and `proof` too when `app-proof.py plan` selects any;
- its first-parent chain merges each named PR's current head, in the order given;
- its base is current `origin/main`, or has the same tested tree (`ci.py tested-key` of both, run from main's tooling: the tree without the Xcode project, scheme and `README.md`), so a `Notchcast: generated files` commit on main that changes only those keeps the proof, and any other change, the Raycast runtime included, ends it;
- the tree land.sh merges has the tested tree of `<sha>`, compared the same way (landing keeps main's copies of the project, scheme and `README.md`);
- each PR is open, and a draft PR only with the `land` label, the lead's sign-off to land it on the train run (a draft runs no PR build of its own; the train run is that build).

Without `--train-run` a draft is refused as always. Covered by a train, the run is all or nothing: a PR that moves or refuses, a red merged-tree pass (still bisected, still refusing when main is red), or main moving before the push in anything but the project, scheme and `README.md` refuses the whole run instead of dropping a PR. Its merged-tree pass runs only the selected harnesses the hosted runner skips (`CI_SKIP_TESTS`), since the train run tested that tree. After landing it deletes the train branch.

Main harnesses (`.github/workflows/main-harnesses.yml`) runs only on manual dispatch, so a branch gets its harness verdict, compile errors included, from GitHub with no local build. Only the Keeper dispatches it (`notchcast-ci.py --keeper`): it is one lane for every branch (the `main-harnesses` concurrency group), where GitHub keeps one run going and at most one pending. It has no push trigger: a branch with a ready PR gets its harnesses from the PR workflow alone, never a second time from a push run. A draft PR's branch or one with no PR gets them from the Keeper's `python3 notchcast/notchcast-ci.py --repo . --keeper` (below), or by marking its PR ready. A run that selects no harness skips the macOS job and concludes success; a branch whose diff `notchcast/lanes.py` says needs no Xcode lane selects none. It does not run on `main`, where Sync's `test_main` runs the full suite on the same commit. Its `plan` job, on Linux, selects the harnesses changed since `notchcast/fork-point.sh origin/main HEAD` (the `Changed harnesses` step prints them) and starts one macOS job for them all, which runs them in one parallel invocation with retries alone and upstream failure comparison, with a 30-minute timeout (an `-f all=true` load test splits the suite over `-f shards=<n>` jobs, default 1). This is not an app build: switches in files no selected harness compiles, UI integration, and main moving between the check and the merge remain outside its protection; the PR build is still required.

`python3 notchcast/notchcast-ci.py --repo . --keeper` pushes the current branch, dispatches main-harnesses.yml on it and waits for the verdict; while a Main harnesses run waits to start it dispatches nothing and prints `QUEUED <url>` (exit 4), and without `--keeper` it refuses, since a worker pushes with `git push` and asks its Keeper for the proof; `python3 notchcast/notchcast-ci-test.py` tests it.

The PR workflow runs one macOS job, `mac`, which runs every lane that needs a Mac in turn (the script tests marked as needing macOS, then `ci-build.sh`: the Debug build and lint, then the whole harness suite), beside its Linux jobs: `linux-checks` (`ci-checks.sh`: the script checks that need no Mac), `linux-harnesses` (the selected harnesses that are in `LINUX_OK_TESTS`, or all of those when the selection is unsure, in the official Swift image pinned by digest), `script-tests`, which runs every other script test (`--all --runner linux`), and `build`, which is green only when every job the diff needs is and only after the build lane ran uploads the `tested-tree-<tree>` artifact. `land.sh` reads `build`: the newest `build` run on the PR head decides, but a cancelled or skipped run (a duplicate dispatch the concurrency rule cancelled) counts only when no other run exists, so it never hides a green run and a failed run newer than the green one still refuses; `design`, `leaks` and `proof` are read the same way. The `route` job asks `notchcast/lanes.py` which jobs the diff (against the PR base, `-f base`, else `merge-base origin/main HEAD`) needs: docs (Markdown outside `Tinycast/`, `Tests/`, `.github/`, `notchcast/licenses/`, `notchcast/vendor/` and `NOTICE.md`, and `docs/`) need none, a `notchcast/` file outside `notchcast/actions/` that nothing in the build names (from `ci-build.sh`, `lanes.py`, the `xcode`, `xcodegen` and `tests` actions, or any path outside `notchcast/` and `.github/`, followed transitively) needs only the script tests (`script-tests`, and `mac` with its build and harness steps skipped), and every other path, an unknown one, any error and any `v2/addons-*` branch needs all. A job the diff does not need is skipped and still reports; `build` accepts exactly those skips and, without `linux-checks`, runs `check-config.py` itself. GitHub runs at most 5 macOS jobs at once for this account, across every branch (measured 2026-11-10 and 2026-11-11: with five running, each further queued job started only when one finished), so everything that runs on Linux does, and a PR run takes one: five PRs build at once, each about as long as its lanes take in turn (a second macOS job per run would halve how many PRs build at once to save the shorter lane's minutes). It does not build draft PRs (converting to draft cancels a running build; `land.sh` refuses a skipped build); mark the PR ready, or dispatch it, to get one.

Shards and the selection are filters on the runner's finished queue in `notchcast/test-harnesses.sh`, so upstream's `Scripts/run-tests.sh` is never patched: `HIDDEN_TESTS` drops hidden features' harnesses from every run, local ones included, and `changed-harnesses.sh` never selects them, `NOTCHCAST_ONLY_TESTS` keeps the named harnesses, `NOTCHCAST_SHARD="<index> <count>"` keeps the harnesses whose name hashes to that index, `CI_SKIP_TESTS` drops what the hosted runner cannot run, only when `RUNNER_ENVIRONMENT` is `github-hosted`, and `HOSTED_ONLY_TESTS` (`config.env`) drops every harness that could touch the Mac it runs on (the keychain, the installed app's data, a permission prompt, a window or focus) unless `RUNNER_ENVIRONMENT` is `github-hosted` or the runner is isolated (below), printing one `SKIPPED <name>: hosted-only` line each. So a local `./Scripts/run-tests.sh`, `land.sh`'s pass and a self-hosted run never run them, and a harness missing from the list is the only one that can. Every harness is in exactly one shard, and it stays in it when other harnesses are added or removed. A run that names one harness (`run-tests.sh <name>`) bypasses the other four, but naming a hosted-only harness off a hosted or isolated runner is refused (`REFUSED: <name> is hosted-only`). `land.sh` refuses a landing whose selection includes one unless a hosted run tested the merged tree (the `tested-tree` artifact of a PR or train run), and names them; `hosted-only-test.sh` and `land-train-test.sh` hold both.

The PR workflow also selects harnesses in shadow (`NOTCHCAST_HARNESS_SELECT: shadow` in `pr.yml`), which changes nothing that runs: `mac` still runs the whole suite and `build` reads the same jobs. When the build lane runs, `route`'s `Harnesses the diff needs` step runs `notchcast/harness-select.py plan`, which asks `changed-harnesses.sh --unsure <file>` for the harnesses the PR diff selects and the reasons the selection is unsure. Unsure means only the whole suite is safe: the selector, `git diff`, `harness_inputs.py` or `lanes.py` failed; the diff touches what selects or runs harnesses (`changed-harnesses.sh`, `harness_inputs.py`, `command-harness-sources.sh`, `test-harnesses.sh`, `ci-tests.sh`, `config.env`, `lanes.py`, `Scripts/run-tests.sh`, `project.yml`, `notchcast/actions/tests/`, `pr.yml`); a path `lanes.py` says the build needs matches no harness file, source pattern, read or kit; or nothing beyond `notchcast-hidden-features-test` is selected. `ci-tests.sh` writes each harness that fails for good (after its lone retry and the upstream comparison) to `$RUNNER_TEMP/harness-failures`, and `mac`'s `Failures outside the harness selection` step (`harness-select.py misses`) reports a failure a sure selection left out as a miss, with a `::warning::` annotation; a run whose tests step did not succeed yet named no harness (the upstream comparison broke, or the suite failed without a `.failed` file) reports `misses=unjudged`. Neither step can fail the run. Every line they print starts with `harness-select`, so `gh run view <run> --log | grep harness-select` shows the plan (`selected=<n>/<suite> unsure=<reasons|no>`) and the run's `misses=<names|none|unjudged>`. A green run has no failure, so only a run with a failing harness tests the selection. Main harnesses and `land.sh` keep the plain selection, without the unsure rule.

Compiled harnesses are cached (`notchcast/actions/tests`, `actions/cache`). `ci-tests.sh` puts `notchcast/swiftc-cache.py` on `PATH` as `swiftc` when `NOTCHCAST_SWIFTC_CACHE` is set: a compile whose key matches copies the cached binary instead of compiling, and the harness still runs. The key is the compiler version, SDK and OS build, the working directory, every argument except the `-o` path, and the contents of every argument that is a file. A compile with an option outside the script's `PLAIN` list, or a directory argument, is never cached, so add a new harness compiler flag there once it is known to name no unlisted input or second output. Each job restores the newest cache of its own name (`pr-<shard>of<count>`, `push-<shard>of<count>`, `release-<tag>`, or `all` for Sync and Snapshot on `main`), else `main`'s `all`, drops the entries it did not use, and saves a new cache only when it compiled something. GitHub lets a branch or PR read its own caches and `main`'s, never another branch's. `python3 notchcast/swiftc-cache-test.py` covers the key and the pruning with a stand-in compiler.

`notchcast/local-ci.sh <pr>` builds and tests the exact PR head on a maintainer machine, through the build queue when one is configured. Before the build it merges the PR onto main with land.sh's own `merge_onto` (`notchcast/merge.sh`, which both scripts source: fork point after a Sync rewrite, union and word drivers, both string catalogs, drift gates, sign-off, defect test, typecheck), so whatever land.sh would refuse fails local CI with the same `REFUSED:` message. It posts `build/local` success or failure with the minutes and the last step or the refusal, and keeps the log in `$NOTCHCAST_LOCAL_CI_DIR/logs/<sha>.log`. Success cancels that head's pending PR Actions runs and supplies build proof to `notchcast/land.sh`.

`notchcast/ready-check.sh [base-ref]` (default `origin/main`) first prints `upstream touch: <files> files, +<a> −<d> (base <upstream merge-base>)` (upstream files modified or deleted) and `delta: <files> files, <lines> lines` against the base ref, and fails as `FAIL footprint` when a branch named `v2/addons-*` other than `v2/addons-core` (or `NOTCHCAST_READY_BRANCH`) changes any path that exists on upstream `main`. A branch cut before a Sync rewrite is judged from its fork point (`fork-point.sh` as it is at the base ref, over the fork's `refs/notchcast/synced/*`), printed as `fork point: <sha>, before a Sync rewrite`: the footprint, the private-data checks, `ci-build.sh`'s `BASE_SHA` and the delete test's trigger diff from there, so the rewritten main is not counted as the branch's change; the drift gates and the tools stay at the base ref. It then runs `land.sh`'s drift gates (`drift-gates.sh` and `check-drift.py` from the base ref, the base ref standing in for `origin/main`) and fails as `FAIL drift`. Next it runs `leaks.yml`'s private-data checks, `check-identity.py diff` and `metadata` as they are at the base ref (on the first install, when the base has no scanner, `HEAD`'s, printed as `identity: bootstrap, scanner from HEAD`), then `HEAD`'s too (it can only add failures), against the base ref, with the caller's `PATH` and none of the git or Python environment `HEAD`'s `config.env` sets, and fails as `FAIL identity: <mode> …` with the redacted locations. It guards against accidental leaks, not a hostile committer: `config.env` is still sourced shell, so it can redefine shell functions before the gate runs. Then it runs every gate `pr.yml` runs, in its order, on the committed `HEAD` against that base, with no PR and no GitHub status: it runs `ci-build.sh` unsharded (harnesses included) in a shared clone under the per-user temporary directory, through the build queue when one is configured. On success it prints `retried: <harnesses>` and `ignored (fails upstream too): <harnesses>` (each `none` when empty), the harnesses `ci-tests.sh` passed only on a lone retry or ignored because they fail on upstream too, then one `PASS` line; otherwise `FAIL <step>` with the log's tail; the full log is `~/Library/Caches/notchcast/ready-check/<sha>.log`. It does not merge onto main, which `land.sh` and `local-ci.sh` add. `ready-check-test.py` fails when `pr.yml` or its local actions gain a step the script does not cover.

One landing hold covers every Mac: `notchcast/hold.sh set [--handover] <owner> <minutes>` (owner: a PR number, or a name the lander passes as `NOTCHCAST_LAND_AS`), `hold.sh show`, `hold.sh release`. It is the repository variable `LANDING_HOLD`; until it expires, `land.sh` lands only the owner's PR, checking at its start and again before each push, and refuses when the hold cannot be read. `set` refuses over another owner's unexpired hold unless `--handover`; the same owner may extend. `land.sh <pr>` also takes the hold itself at its start when there is none (value `<pr> <expiry> auto <host>:<pid>`, `NOTCHCAST_LAND_HOLD_MINUTES` long, default 150), so the lander that started first is never refused at the end by a hold set during its harnesses; it refuses at the start under another owner's live hold, takes nothing under its own, renews it for another `NOTCHCAST_LAND_HOLD_MINUTES` before each push while it is still exactly the value it wrote, and at every exit (even after a failed claim) releases the hold only if it is still exactly the value it wrote. A SIGKILL skips that release, so an `auto` hold whose lander ran on this Mac and is no longer running counts as no hold (`hold.sh show` says so); one from another Mac still holds until it expires. A train takes one hold, named for its first PR; under a live hold that names one of its PRs it lands only that PR. Meanwhile the owner's `local-ci.sh` build takes the build queue's landing lane, ahead of every normal job, and any other PR's `local-ci.sh` waits until the hold ends; an `auto` hold does neither, so a landing does not stall other builds.

PRs carry no generated files: edit their inputs, regenerate locally before using Xcode (`xcodegen generate`), and leave the generated diff uncommitted. PR CI regenerates the Xcode project before building, not the Raycast runtime. After each source push to main, the Generated files workflow runs `ci.py regenerate` on a fresh `origin/main` in a job with a read-only token and no stored credentials, and a second job, which runs no generator, commits only `GENERATED` as `Notchcast: generated files` with the repository identity onto the `main` they were generated from and pushes; if `main` moved meanwhile it pushes nothing, as the run that push started regenerates. Its generated-only push is excluded by path filters, and the Actions token starts no further workflow runs. If it waits out a Sync replay past its 60 min timeout and that replay fails, main keeps stale generated files until the next source push. Sync regenerates before every build too.

A run also sweeps the throwaway `UserDefaults` suites it left in `~/Library/Preferences` (`notchcast/pref-sweep.py`, hooked from `test-harnesses.sh`): the last run to finish deletes the new plists named like a suite `Tests/` builds (a literal prefix followed by a UUID, or an app domain with "test"), whether the suite passed, failed or was killed, and never a file that existed when the run began or a real app domain. Any other new UUID-named plist is left and printed as `pref-sweep: left <n> unknown`, so a harness shape the prefixes miss shows up instead of being deleted on a guess.

Fork harnesses are discovered by `notchcast/test-harnesses.sh`, so a PR never edits `Scripts/run-tests.sh`. `notchcast/harness_inputs.py` resolves inputs for that runner, `changed-harnesses.sh`, and `check-module-harness.py`. `check-module-harness.py` (the `module-harness` step of `ci-checks.sh`) fails when the PR adds a `*Module.swift` that no harness compiles. `Tests/nc-<Folder>-<name>-test.swift` compiles all Model and Service sources of `Tinycast/Features/<Folder>/`. A `// notchcast-sources: <compiler arguments and source globs>` or `// notchcast-kit:` header overrides that folder rule. Other fork harnesses (`Tests/notchcast-*-test.swift` or an upstream-style name) declare their sources in one or more such lines. Paths contain no spaces. For upstream-registered harnesses it also reads the `run` arguments from `Scripts/run-tests.sh`, resolving its variables and continued lines without duplicating those source lists. The resolver includes conditional additions from `command-harness-sources.sh` in one Bash invocation; registration appends only inputs not already supplied by the upstream `run` line. A resolver failure (including malformed headers or a failing conditional helper) emits `::error::` and terminates the runner rather than passing an incomplete suite. A `notchcast-*` harness without the header fails alone with an error; the rest of the suite still runs, and so does a fork-added upstream-style harness (absent from the upstream merge base) that loses its header (a `// notchcast-reads:` line alone does not count). The resolver fetches a missing `upstream/main` ref from `UPSTREAM_REPO` in `config.env` to tell which harnesses are fork-added, and a failed fetch is a resolver error; outside a git repository (a `git archive` copy, as `notchcast-precompile.py` uses) the fork-added check is skipped. A `// notchcast-kit: <name> [<name>...]` header expands to the globs and compiler arguments listed one per line, `#` comments allowed, in `Tests/Kit/<name>.kit`, so harnesses name a shared source set instead of copying its file list (`notchcast-command-icons` is the first); an unknown or empty kit is a resolver error, and changing a kit file selects every harness that uses it.

A `// notchcast-reads: <globs>` header declares repository files a harness reads as text or compiles in a child process. Multiple lines are combined. For example, `// notchcast-reads: notchcast/*.py` makes script changes select the harness without adding them to its compiler arguments. Selection matches the patterns against changed paths, including deleted files. Recursive read sets use `**`, for example `Tinycast/Features/**/*.swift`.

`notchcast/script-tests.py` recursively discovers `notchcast/**/*-test.py`, `*-test.sh`, `*-test.mjs` and `*-test.swift`, including tests directly in `notchcast/`, and runs them with Python, Bash, Node and Swift 6 respectively, one per CPU at a time (`--jobs`), each with its own `TMPDIR`. It prints each test's whole output when that test ends, then a `passed, failed` count, and any failure fails the run. `ci-build.sh` runs it when `pr.yml` does not run it in its own job (local CI, `ready-check.sh`); there `land-test.sh` runs only when the diff against `BASE_SHA` (else `origin/main`) touches a file listed in `notchcast/land-tooling.txt` (`land.sh`, the shell files it sources, and `fork-point.sh`) or itself. `pr.yml` passes `--all`, so every PR build runs every test: `--runner macos` picks the tests with a `# script-tests: macos (<why>)` line (the tool they test needs macOS: `xcrun`, `ditto`, `PlistBuddy`, BSD `sed`, `date` or `mv`), `--runner linux` the rest. A new test runs on Linux unless it carries that line. `land-test.sh` runs `land.sh --check` on real merged trees and compiles one real harness (`notchcast-hidden-features-test`, the one its fixtures break) per landing; `bash notchcast/land-test.sh --full` runs each fixture's whole selection instead (97 harnesses, twice). `install-app-test.sh` drives `install-app.sh` against synthetic bundles with fake `open`, `osascript` and `launchctl` on `PATH`. Pass `--list` for the default paths or `--all --list` for every discovered path. Run it from the repository root; finding no tests is an error.

## Linux

`LINUX_OK_TESTS` (`config.env`) names the harnesses that compile and pass on Linux, where Foundation is swift-corelibs-foundation and no Apple framework exists; every other harness is mac-only. That one list decides three things. `Scripts/run-tests.sh` on Linux runs only those harnesses and names the mac-only ones it skipped; one that is also in `HOSTED_ONLY_TESTS` is skipped there as hosted-only, as on a Mac (`notchcast/linux/lockf` stands in for `lockf` with `flock`). A harness joins the list after it passed on Linux and on a Mac: `./Scripts/run-tests.sh <name>` runs a single one on either system, listed or not, unless it is hosted-only. Swift 6 comes from `swiftly` or the distribution's package, with nothing else to install.

Before a push from a Linux machine, run the harnesses the branch changed, through the build queue where the machine has one: `NOTCHCAST_ONLY_TESTS="$(bash notchcast/changed-harnesses.sh origin/main HEAD | xargs)" python3 ~/Code/chad-v2/gate.py build -- ./Scripts/run-tests.sh`. Green there covers only the linux-ok part of the selection; the mac-only harnesses it names still need the macOS run.

`land.sh` on Linux lands a PR itself when the merged tree's diff reaches only `LINUX_OK_TESTS` harnesses, touches no `LINUX_DENY_INPUTS` path and no file that selects or runs harnesses, and those harnesses pass there. The always-run harness counts only when the diff reaches its inputs, and a path no harness names does not count: a Mac landing runs nothing more for it. A hosted-only harness in the selection is never proven by the Linux run, on any runner: without a hosted macOS run of the tree the landing is refused, naming it. Anything else it does not refuse: it prints `ROUTED:` with the reason, hands the PR numbers to the `notchcast_mac_route` hook and exits 4. A tree a hosted macOS run already tested lands from either system.

Every landed commit's message ends with `Landed-from: linux` or `Landed-from: mac`, where its harness proof ran: `git log --grep '^Landed-from: linux' origin/main` counts the share. Snapshot runs the whole macOS suite on each pushed main, and `land.sh --guard` reads that run for each commit landed from Linux; every landing runs it first, and it can run alone on a timer. Green is recorded as the commit status `FOLLOWUP_CONTEXT`. Red, when the commit is still main's tip and the only change since a green main: it lands a revert through a `revert-<pr>` PR, adds the paths of that diff that the failed harnesses take as inputs to `LINUX_DENY_INPUTS`, reopens the PR with the failing run linked, and tells `notchcast_notify`. Red with anything landed on top, or beside another unjudged Linux landing: no revert, only the report. Snapshot cancels its run in flight on each new push, so a busy main judges a Linux landing by the first later run that finishes.

## Runners

Every macOS job runs on GitHub's hosted `xcode-27` image (free on this public repository), and every other job on `ubuntu-latest`. A job is a macOS job only when it runs `xcodebuild`, compiles a harness, signs, or launches the app; Generated files (`generated.yml`) is not one: on Linux `ci-xcodegen.sh` builds the pinned XcodeGen tag from source, and `notchcast/actions/xcodegen` caches the binary. GitHub runs at most 5 hosted macOS jobs of this repository at once, and the rest queue, so a run of PR, Main harnesses or Delete check has one macOS job, and Snapshot two: one runs the tree with no secret, one only signs.

Two jobs can move to a self-hosted Mac, and only in a `workflow_dispatch` run (what `notchcast-ci.py` and `train.sh` start): `mac` in `pr.yml` and `harnesses` in `main-harnesses.yml` then take the runner label in the repository variable `NOTCHCAST_MAC_RUNNER` (`gh variable set NOTCHCAST_MAC_RUNNER -b <label>`; delete it and they are back on `xcode-27`; `-f hosted=true` on a dispatch keeps that one run hosted). They hold no secret, and a run on a maintainer's working Mac is cut down to what cannot touch it: `test-harnesses.sh` skips the harnesses in `HOSTED_ONLY_TESTS` (`config.env`: every harness that names an API able to show a window, take focus, launch an app, or reach the keychain, pasteboard, sound, events or preferences; `ci-tests-test.sh` fails when such a harness is not listed) with a `SKIPPED` line each, and `mac` skips the macOS script tests with a `SKIPPED on a working Mac` notice; `build` uploads no `tested-tree` artifact for it, so it proves no tree, and a train run whose Mac job ran there fails. An isolated runner (a separate macOS user with its own keychain and no access to a maintainer's home) runs everything a hosted one does, the hosted-only harnesses and the macOS script tests included: it has `NOTCHCAST_ISOLATED_RUNNER=1` in its own service environment, which whoever installs the runner sets and no workflow or script in this repository may (`hosted-only-test.sh` fails when one does). Its green build is landing proof within limits: `build` uploads `tested-tree-isolated-<key>` (never the hosted `tested-tree-<key>`, so Sync still tests that tree itself) with the runner's toolchain stamp (`xcodebuild -version`, then `sw_vers`) and the harnesses it excused, the ones red there and on upstream, which `ci-tests.sh` ignores for the verdict and the run therefore proved nowhere. `land.sh` takes that record when no hosted run tested the tree (`ci.py isolated-proof`): it refuses a stamp other than `ISOLATED_TOOLCHAIN` (`config.env`; change it only after comparing a hosted and an isolated run of one commit), refuses when a selected hosted-only harness was excused (only a hosted run can prove that one), and runs any other selected harness the record excused in its own pass; everything else the selection names is proven, the hosted runner's `CI_SKIP_TESTS` included. `train.sh` sends a train's Mac job to that runner while the variable is set and a runner with that label is online (with none online the job would stay queued, so the train goes hosted and says so), and says which runner on its first line per train; `NOTCHCAST_TRAIN_MAC=hosted notchcast/train.sh <prs>` keeps one train hosted, which is also what a refusal above asks for. `NOTCHCAST_TRAIN_ONTO=<tip of a running train> notchcast/train.sh <prs>` builds the next train on that tip instead of on main, so two trains run at once on two runners; `land.sh` accepts it only after the first has landed (it compares the tested tree of the train's base with main's) and never by itself, and a red first train means running the second again. The runner keeps its work folder between jobs, so its build is incremental where a hosted one is clean. A `pull_request` run always stays on `xcode-27`, so hosted capacity keeps working beside the self-hosted Macs, and since this repository is public, no fork's code reaches them: a fork cannot dispatch. `ready-check-test.py` fails when a job names any other runner, or that variable outside this exact expression: `${{ github.event_name == 'workflow_dispatch' && !inputs.hosted && vars.NOTCHCAST_MAC_RUNNER || 'xcode-27' }}`. Every job that signs, pushes or launches the app (Sync, Snapshot, Proof, Delete check) stays hosted.

A dispatch can also send `pr.yml`'s `mac` job, cut down to the harnesses, to a runner it names: `gh workflow run pr.yml --ref <branch> -f harness_runner=notchcast-mba`. That label is the MBA lane: `mba-notchcast-1`, a runner in a sandbox under a maintainer's own account, which cannot run `xcodebuild`, write outside its own folders, open a loopback port, or reach the keychain, the clipboard or a window. A harness-only run checks the runner's Xcode by its version file (`ci-xcode.sh` under `NOTCHCAST_XCODE_FROM_RUNNER=1` reads `DEVELOPER_DIR`, which the runner sets), runs the suite without the compiled-harness cache (its key asks `xcrun`, which starts `xcodebuild`), and skips everything else: the build lane, the macOS script tests, every Linux job and `build`. It tells early whether a branch's harnesses pass, taking neither a hosted Mac nor the MBP, and it never proves a tree: it is a `working` run on any runner and uploads no `tested-tree` artifact, its `build` check is skipped (`land.sh` refuses a head with only that one and ignores it beside a real run's), and on a `train/` branch it fails in `route`, since `train.sh` reads a train's PR run by its conclusion. Its concurrency group ends in the label, so it never cancels the branch's real run. A self-hosted working runner names the harnesses it cannot run in `NOTCHCAST_RUNNER_SKIP_TESTS` (space separated, in the runner's own `.env`): `test-harnesses.sh` drops them from a whole-suite run with one `::notice::SKIPPED on this runner: <name>` line each, and a GitHub-hosted runner, an isolated one and a local run ignore the list (`hosted-only-test.sh`). So in `pr.yml` the expression is `${{ github.event_name == 'workflow_dispatch' && (inputs.harness_runner || !inputs.hosted && vars.NOTCHCAST_MAC_RUNNER) || 'xcode-27' }}`: with the input empty it is the one above, and `ready-check-test.py` holds that no event but a dispatch leaves `xcode-27`.

The harnesses in `CI_SKIP_TESTS` (`config.env`) cannot run on the hosted VM, so they run in no CI workflow and are dev-loop only: `ClipboardTextTests` (Vision OCR fails in the VM with `CRImageReaderError`) and `FormInputTests` (capturing rendered text fails in the VM). Run `./Scripts/run-tests.sh ClipboardTextTests` on the MBA when it is idle, after a change that selects it; `land.sh` runs it, when selected, in its local merged-tree pass. `FormInputTests` is hosted-only as well, so it runs only on an isolated runner, and `land.sh` prints it as `SKIPPED, proven by no run`.

## Drift gates

`python3 notchcast/check-drift.py` checks fork-owned Swift against `notchcast/drift-baseline.json`. It scans production sources under `Tinycast/`. Ownership comes from files added since the merge base of `HEAD` and `upstream/main`, including working-tree additions. The checker fetches the upstream ref from `UPSTREAM_REPO` in `config.env` only when that ref is missing. Upstream-owned Swift is read for references but never gets a gate budget.

The baseline maps each rule to stable keys and integer counts. Each key occupies one line to reduce overlap, but reductions to adjacent keys can still conflict. Keep retired keys at zero instead of deleting them; `--write-baseline` preserves them. A new finding or a higher count fails. A lower count also fails with `lower it in drift-baseline.json`, so removing debt requires lowering its budget in the same change. `--write-baseline` seeds the initial file or tightens existing counts, but refuses growth. `--compare-base <commit>` rejects every added or raised entry, including alert thresholds and zero-valued new keys; a `path` or `path:name` key whose file git pairs as a rename (`-M`) is compared under its old path, while clone and boundary keys are not followed, so a move that changes them still reads as growth. A base without the file permits its first installation.

| Gate | Rule and key |
| --- | --- |
| 1 | Feature-to-feature lexical type references are counted by folder pair. A feature may use its own types, upstream types, `Platform/`, and the reviewed `KERNEL` set in the checker. `NotchcastCore.<member>` lookups outside the kernel are counted per file. Fork files inside upstream feature folders are counted per file. |
| 2 | Production files over 400 lines and fork harnesses over 600 lines are counted by path and exact line count. The planned harness limit is 400 at phase 5. |
| 3 | Types and top-level or static/class members with no production use are counted as `path:symbol`. A name found only in tests gets a separate `test-only` budget. Indented instance functions and properties are skipped to avoid treating SDK callbacks as dead code. Overrides, Objective-C entry points, `@main`, and property wrappers are exempt. The check is lexical, not a compiler reachability proof. Reused names can hide findings. |
| 4 | jscpd checks a temporary copy of fork production Swift for clones of at least 70 tokens and 6 lines between different files. The key is an unordered file pair, and the count is its clone count. jscpd and its whole dependency tree are pinned with integrity hashes in `notchcast/jscpd/package-lock.json`, installed once per lockfile with `npm ci --ignore-scripts` under `~/.cache/notchcast/`. Missing npm, a failed install or invocation, a 120-second timeout, or a missing or malformed report fails closed. Lowercase literals beginning with `app.notchcast`, `notchcast.`, `com.notchcast`, or the preference-domain prefix `com.apple.` are counted by literal and number of owning folders. Icon names and standard protocol strings are outside that scope. The planned clone threshold is 50 tokens at phase 6. |

A line ending in `// drift: keep <reason>` exempts that line. A file-size exception uses that marker on the final line. Empty reasons do not waive anything. Boundary checks reuse `notchcast/bin/swiftgraph.py` and its literal stripper and file graph. The checker disables Python bytecode writes.

`land.sh` refreshes `upstream/main` before merging so upstream additions are not charged to the fork. It runs the baseline comparison and all four gates on each merged candidate, including retries after main moves. The gate checker and its imported graph code come from the landing base, not the candidate; the first installation uses the invoking checkout when the base has no checker. Tests cannot prove a gate change safe, so a change to `notchcast/check-drift*`, `notchcast/bin/swiftgraph.py`, `notchcast/config.env`, or a file listed in `notchcast/land-tooling.txt` (the same list that triggers `land-test.sh`) is a visible sign-off: landing refuses unless the PR body has a line `Drift tooling: <reason>`, and that line is kept in the squash commit. For the drift tooling itself, the landing base's `check-drift-test.py` also runs against the merged tree with `python3 -I`, as a sanity check only, and a PR that deletes that file is refused. A budget increase refuses with `REFUSED: drift baseline grew`. Other drift failures re-run the checker on the base, print `main is already red` when that also fails, and refuse with `REFUSED: drift` either way. The pre-push hook runs gates 1 to 3 without npx and warns rather than blocking. `land.sh` and `local-ci.sh` share these gates through `drift-gates.sh`; they run locally, not in `ci-build.sh` or an Actions workflow.

A PR whose title starts with `Fix ` after removing an optional `Notchcast: ` prefix, case-insensitively, must add or change a `Tests/*-test.swift` or `notchcast/**/*-test.*` file. Otherwise landing refuses unless the PR body has a line `No test: <reason>` with a nonempty reason. That line is retained in the squash commit. This is the cheap presence check only. It does not prove that the changed test failed on the base commit.

A run of all four gates, which is what `land.sh` and `local-ci.sh` do, ends with the counters (each rule's total against its baseline total, and the pattern counters `try?`, `Task.sleep`, `Process()`, `tool-paths` and `cancellation-loops` in fork production Swift), so the log shows how close each limit is. Each key above its limit prints one machine-readable line, `GATE-THRESHOLD <rule>:<key> <value> <limit>`, such as `dead:<path>:<symbol>` or `clones:<path>|<path>`; a pattern counter prints `GATE-THRESHOLD <counter> <value> <limit>` against its threshold in the baseline's `alerts` map. A pattern crossing whose value does not exceed what the merge base with `origin/main` already had ends with `known`, so only lines without it are new. A new or grown one fails the run with `threshold breach new or grown: <counter> <value> > <limit> (main: <value or none>)`, so `land.sh` refuses it; when `origin/main` counters cannot be read, a `WARN` replaces the failure. The pre-push subset (gates 1 to 3) prints none of this. A reviewer gets only the goal and the diff ([docs/review.md](docs/review.md)).

Nothing runs after landing: a check that only reports or files a task does not exist; it blocks before the merge or it is removed. The retired report counters (`file-lines`, `test-lines`, `waivers`, `upstream-patch-lines`, `fix-no-test`) still sit in `alerts` only because the v2 base checker requires them; the current checker ignores them.

`python3 notchcast/check-drift-test.py` plants boundary lookups, oversized files, dead and test-only declarations, generated clone blocks including one at exactly the jscpd limits (70 tokens, 6 lines), and copied fork/preference literals. Each deliberate violation must exit 1 at its gate. It also checks waivers, SF Symbol exemptions, fail-closed clone checking, baseline tightening, and new, grown and known pattern-counter breaches. `python3 notchcast/land-drift-test.py` exercises the actual landing budget comparison, defect-test presence rule, `Drift tooling:` sign-off, base-fixture run, and a refused pattern-counter breach. The older merged-tree harness fixtures isolate these gates because the drift fixtures test them separately.

## Snapshot releases

`.github/workflows/snapshot.yml` starts primarily on pushes to main, with a cron backstop at minutes 7, 27 and 47, and by manual dispatch. Workflow-level concurrency holds the `snapshot` group through planning, building and publishing; `cancel-in-progress` is true only for a push, so a newer main supersedes the run in flight while cron and dispatch runs queue behind it. Automatic runs plan at once: unchanged main skips, otherwise the tag's timestamp is the later of now and 50 minutes after the latest snapshot's publication (its release's `published_at`, when it reached the Macs), so two publications are always at least 50 minutes apart. The macOS build of that pinned main starts straight away, while the `gate` job waits on Ubuntu until the tag's timestamp; publish needs both, then refetches main and releases and skips with a notice when main has moved, or fails when the latest other snapshot was published under 50 minutes ago. A run cancelled while publishing deletes its draft release and its tag, unless a published release already uses that tag. Manual dispatch never waits in the planner: unchanged main fails with an error; a closed gate exits successfully with a notice including its UTC opening time. A dispatch can still be cancelled while pending when a newer run replaces it: it ends grey "cancelled", never green, and the replacing run builds current main. Sync's deploy-key and land.sh's authenticated pushes trigger Snapshot; Generated uses GITHUB_TOKEN, so its pushes rely on the backstop. A build that finishes before its gate opens publishes when the gate opens, subject to GitHub scheduling. Failed attempts do not block retries. Snapshot planning tests run only in this workflow, before planning.

To publish a waited-for fix early, first cancel any Snapshot run still building or waiting in `gate` (it holds the `snapshot` group; cancelling it before `publish` publishes nothing): `gh run list -R kaczordodgers/notchcast -w Snapshot -s in_progress`, then `gh run cancel <id> -R kaczordodgers/notchcast`; then `gh workflow run Snapshot -f skip_gate=true -R kaczordodgers/notchcast`. It bypasses only the 50-minute gate, retaining unchanged-main protection and every test, lint, signature, identity and launch check.

Generated files retries runner allocation at most twice when its `regenerate` job was cancelled before any step started, its `push` job never ran, and has GitHub's hosted-runner not-acquired annotation; script failures and exhausted allocation failures remain red.

The workflow regenerates the project and uses sync's `notchcast/actions/tests` action on the captured main commit, including hosted-runner exclusions, retries and comparison against pristine `merge-base(main, upstream/main)`; it skips that action when the main commit already has a green `TESTED_CONTEXT` status from Sync. Lint must also pass. Either failing fails the snapshot without publication; Leaks is independent. Tests and lint run first in the `build` job, which holds no secret and builds the app only after them; the `snapshot` job signs what `build` packed without running the tree's code, and `publish` needs it green. They use sync's release and sign actions. Build or signing failures publish nothing. Snapshot tags point to that exact main commit and use the repository identity.

Tags append `.snapshot.YYYYMMDDHHMMSS` (UTC) to the newest published upstream mirror version, for example `v0.12.7-beta.131.snapshot.20261104120000`. The app version and asset names include the suffix. The updater selects only non-draft releases whose tags end in `.snapshot.` followed by exactly 14 digits, ordered by that timestamp alone. It ignores upstream mirror, beta and stable releases, regardless of their version or publication time. An installed non-snapshot version is replaced by the newest snapshot. An installed snapshot with a later timestamp is kept, and one with the same timestamp is kept when signed by us. Sync's mirror parser ignores snapshot tags. Existing updater copies must be refreshed to use timestamp-only ordering. Updater selection checks run with `bash notchcast/update-install-test.sh`. Snapshot planning checks run with `python3 notchcast/snapshot-test.py`.

Enable independent 30-minute installs on an installed Mac from its checkout with `/bin/bash notchcast/install-launchd.sh update --auto-install`. This reloads only `notchcast.update`, with `update.sh --install` in its arguments, and runs at load and every 1800 seconds. It never changes `general.automaticallyCheckForUpdates`. Run `install-launchd.sh update` to restore preference-respecting behavior. First-time setup can use `install-launchd.sh all --auto-install`.

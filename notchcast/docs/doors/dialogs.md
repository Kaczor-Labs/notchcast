# Door: Dialogs

**Dialogs** go through `context.confirm(title, message, confirmTitle)`, Notchcast's own yes/no dialog (`AppCore.confirm`, neutral tone), or `context.confirmDestructive` with the same arguments when the step loses something (danger tone, destructive button), never `NSAlert`; `NotchcastCore` sets both on every context, and both are nil in harnesses, which set their own (`guard let confirm = context.confirmDestructive, await confirm(…)`).

**Hidden text** goes through `context.askSecret(title, message, fieldTitle, confirmTitle)`: the same dialog with one hidden field (`DialogController.askSecret`, a `.secret` accessory on `RevealableSecureField`), answering the typed text, or nil on Cancel or Esc; nil in harnesses like the other two. Notchcast's own line under the field names the asking add-on (its first switch's title), so a prompt cannot pass itself off as a system password dialog. The text lives only in the dialog's state and the returned value: never in the title or message, never logged, persisted or written to the pasteboard, and cleared when the call returns. The field has focus on open, ↵ confirms, ⌘V pastes. Unlike every other dialog it does not cancel on click-away, so the user can fetch the secret from a password manager. Secure Input is on while the dialog is key, also while the text is shown, and off once it stops being key or closes for any reason, so Hyper, snippets and event taps work again. Proven by `Tests/nc-Notchcast-ask-secret-test.swift` (hosted only) and `Tests/nc-Notchcast-secure-input-hold-test.swift`.

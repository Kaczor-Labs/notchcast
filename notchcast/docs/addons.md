# Notchcast add-ons: the contract

Every Notchcast feature on top of Tinycast is an add-on. An add-on plugs in with one line and comes out with one line, and syncing with upstream stays a non-event. This page says what an add-on may touch, what the core does for it, and how each promise is checked. It replaces v1's `feature-descriptors.md`, `command-hook.md` and `switch-paths.md`.

## 1. What an add-on is

- **Built fresh, never ported.** No feature copies or ports code from v1 (branch `v1/final`) or any local pre-v2 branch; each is written on the island base, with outside projects (Aural, Vorssaint, RemoveMacAI, Peel and the like) as references, credited in `notchcast/licenses/borrowed.md` when code is taken.
- **One folder:** `Tinycast/Features/Notchcast/<Folder>/`. The folder holds every source the add-on needs. It may hold `Model/` (no AppKit or SwiftUI; every environment fact injected), `Service/`, `UI/` and `Settings/`, plus its own string catalog `<Folder>.xcstrings` (table `Notchcast<Folder>`, English only).
- **One registration line** in the fork-owned registry `Tinycast/Features/Notchcast/NotchcastRegistry.swift`, a single array with one `<Folder>Addon.self,` per line. `.gitattributes` gives that file a union merge, so two add-on PRs that each append a line merge without a conflict.
- **Its harnesses** live at `Tests/nc-<Folder>-*.swift`. `notchcast/harness_inputs.py` finds them by their header, so there is no list to edit. An add-on never edits a core harness (`Tests/nc-Notchcast-*.swift`): what the core checks per add-on, it finds by reading the folder and its own harnesses, so the delete test leaves every core harness compiling.
- **Several switches in one folder** are allowed when they share code: Downloads + aria2 + Distill + Timestamps + Torrents + Wi-Fi and iPhone bonding ([downloads-bonding.md](downloads-bonding.md)), Brightness + Volume (one media-key policy). They are then added and deleted together. Two folders never share code; if both need something, it moves into Core as a service with a reason.
- **Nothing else.** An add-on edits no upstream file, no other add-on, no Core file, no shared list, no `Localizable.xcstrings` and no generated file (`Tinycast.xcodeproj` is regenerated by CI and never committed).

## 2. What the descriptor declares (the core does the wiring)

`<Folder>Addon` conforms to `NotchcastAddon` and states, as plain data:

- `switches`: one per user-facing feature: frozen string id (the v1 raw value where one exists; an id v1 never had is declared in the folder, at column 0 of any of its files, as `// notchcast-new-switch-ids: <id> [<id>...]`), title, subtitle, `category`, `defaultEnabled` false unless v1 shipped it on, `dependencies` (switch ids, may name another folder's switch: the core then turns it off when that folder is gone), `requiredGrants`.
- `commands`: launcher commands, each with id `command:nc-<slug>` (frozen), name, symbol, owning switch, `run`. They appear as ordinary launcher entries of the existing `AppEntry.Kind.command`, owned by the Notchcast tab holding their switch (`settingsOwner: .notchcast(<pane>)`), so there is no new launcher section and no category guessed from an id; their icon is a tile of their symbol in that tab's tint, set as the entry's `iconOverride` because upstream draws a `.command` only from `CommandID` (#909), and proven by the add-on's own icon harness (§5); the stock Commands category neither lists nor gates them, and their alias and hotkey fields sit under their switch.
- Commands known only at run time (one per device, say) come from the running module: `context.setCommands(_:)` replaces the module's own list, and the launcher, hotkeys, Settings rows and the launcher's Hide follow at once; they go when the module stops. `context.handleLauncherShown(_:)` runs each time the launcher opens, so the module can refresh what it lists. Their slugs are built from stable facts, never a counter, since aliases and hotkeys are stored under them. Taildrop is the first user.
- `hotKeys`: commands may be bound like any built-in command, stored at `hotkey.command:nc-<slug>`, the same key v1 used, so existing `nc-screenshot-area` and `nc-screenshot-display` bindings resolve unchanged.
- `settings`: extra rows under each switch, written as SwiftUI views inside the folder; the core renders them in the add-on's category section of its tab.
- `taps`: event-tap subscriptions (event mask plus handler). The core installs one shared tap only while at least one enabled switch subscribes, and removes it when the last unsubscribes. Subscribed does not mean live: an add-on that acts outside its handlers checks `context.isTapLive`, and each tap's `reset` runs when the tap drops on its own.
- `makeModule(context)`: start and stop. The core builds the module when the switch and its dependencies are on and stops it when they go off. `context` is the only door to the app: preferences store, presentation seam (island), tap hub, launcher hooks, Core services (process runner, clock, transcription), and clipboard history's write pair: an add-on that writes `NSPasteboard.general` calls `context.prepareClipboardMutation()` before the write, so the user's last copy reaches history first, and `context.synchronizeClipboard(changeCount:)` after each of its own writes, so the poller never records them; `NotchcastCore` wires both to `ClipboardManager`'s own pair, the one `TextInjector` uses. An add-on never reads `AppCore`, `NotchcastCore` statics or another add-on.
- `context.setUnavailable(entryIDs)`: a running module names the commands it cannot run right now (Noise Control: modes the connected headset lacks); the launcher drops them and their hotkeys still run, so a press reports why. Stopping the module clears it.
- `makeRecovery(context)`: optional, default `nil`. Built and started at core start whatever the switches say, before any module, and stopped at core stop after the modules. It repairs what a previous run left behind (a dirty journal) with the add-on off, so it stays short. It gets its own context, so switching the add-on off and on leaves its tap subscriptions in place; they still install only while their switch is on, and core stop clears them. A module reaches its own add-on's recovery with `context.recovery(RecoveryType.self)` (nil before core start, after core stop, or when the add-on has none), so work it hands over, such as a pending restore, survives the switch going off. A URL or file opened with the app goes to the add-ons' `context.handleOpenURL` claimers, every running module first, then every recovery, so a recovery can answer one with the add-on off: Downloads' recovery refuses a magnet or `.torrent` out loud while every Downloads switch is off.

**Presentation** is the island's own API: `context.presenter` is `any IslandPresenting`, and add-ons post the Island value types (`IslandLevel`, `IslandNotice`, `IslandStatus`, `IslandMenuRow`; notchcast/docs/island-shell.md "Presentation API"). `NotchcastCore` hands the controller `core.islandPresenter`, the island's own presenter, with no add-on stand-in between; what each call draws is the island's (island-shell.md).

**Transcription** goes through stock Dictation: `try await context.transcribe(audioURL)` returns the text of an audio file in the user's own Dictation model and language, decoded and recognized off-main, or throws `NotchcastTranscribeError` (`unavailable`, `busy`, `unreadableAudio`, `failed(message)`). It refuses with `.busy` while the user is dictating (recording or still transcribing) and while another add-on's transcription runs; it never queues behind or interrupts the user. When the user starts dictating mid-run, stock Dictation signals the core directly and waits, before its microphone opens, until the add-on's model call is cancelled and cleaned up, so the user's dictation is never refused busy; the add-on gets `.busy`, also when that dictation already ended, and no further piece of its audio enters the model. A cancelled caller gets `CancellationError`, never the text or `.busy`. `NotchcastCore` injects the one hook (`NotchcastTranscribing`, implemented by `NotchcastDictationBridge`), so no add-on and no Core file names a Dictation type; harnesses pass a fake (`Tests/NotchcastDictationFixture.swift`).

**Settings backup** goes through the stock format: `context.settingsBackup` (`NotchcastSettingsBackup`) gives the current settings as Backup › Export's settings JSON (capability flags such as `snippetsEnabled` already left out), calls back once on the next change to them, writes them as a settings-only `.tinycast` file atomically, and restores one through the stock import with its confirmation and report. `NotchcastCore` injects `NotchcastSettingsBackupBridge`; harnesses pass a fake, and the default writes nothing.

**Apple Events** to another app go through `NotchcastAppleEvents` (`Core/Service/`): `values(bundleID, path, refusing:)` sends one `core/getd` read, 5 s, and `finderSelection(refusing:)` returns Finder's selection as file URLs. Both are synchronous, so the add-on calls them off the main actor. A failed read hands its status to the add-on's `refusing` closure and reads as empty unless that throws, so each add-on keeps its own failure states. It is in Core because Copy Path and Taildrop both read Finder (§1: two folders never share code).

A switch with none of commands, settings action, taps or a module has no user path and fails the registry harness (v1 shipped 35 such switches).

**Ownership.** There is one `NotchcastCore` instance, created by H1 inside `AppCore.start` and held by `AppCore`; it stops every module and removes the tap when the app terminates. Hook statics in upstream files are `@MainActor`, set once in `start`, and `nil` means stock behaviour. No second actor, no new `MainActor.assumeIsolated`.

**Debug scenes and probes** of an add-on live in its folder, so the delete test removes them. Nothing of an add-on goes into `IslandVerification` or any other shared scenes file.

## 3. Upstream hooks: the whole footprint of the add-on system

Only `v2/addons-core` touches upstream files, and only through these hooks. Each hook is a general injection point declared with stock types (a closure or static the core sets in `start`). No upstream file a harness compiles names a fork type. One upstream harness needs a fixture all the same: `Tests/AppInstallationTests.swift` stubs `HotKeyAction` and compiles `VisibilityStore.swift`, so its stub carries H4's case (+1); the dummy delete test found it.

Known cost: a future upstream exhaustive `switch` over `HotKeyAction` or `SettingsTab` breaks our build with no textual conflict; the sync rehearsal's ready-check is what catches it. Every upstream exhaustive switch that needed an arm is listed in this table and counts in the budget.

**Budget for `v2/addons-core` is a gate.** The numbers (files, +lines, −lines) live in one fork-owned file, `notchcast/addons-budget.env`; ready-check fails `v2/addons-core` above them. Raising the budget is a visible one-line change with the reason in the commit body. Starting estimate 10 files, +34 −5 (F9 and its H10 dropped 2026-11-15); the env file now holds the real footprint of the first READY. `notchcast/check-addons.py` runs in `ci-checks.sh` (so in ready-check and CI): core mode prints each upstream path with its +/− and fails above the budget; feature mode fails any path outside the branch's folders, its tests and `<Type>.self,` registry lines; `--mode` (core, feature or none) or `--branch` is required, and `ci-build.sh` passes the branch, which is core only for exactly `v2/addons-core` or `v2/addons-core-<n>` (the name a rebased core is pushed under since nothing force-pushes), feature for any other `v2/addons-*`; on every branch a reference guard fails a fork-added line outside an add-on's folder that names its switch ids or slugs, or names one of its top-level types in code (strings, comments and nested types do not count; its registry line, other add-ons' `dependencies:` arrays and the core harnesses `Tests/nc-Notchcast-*.swift`, which pin the frozen ids, are exempt). v1 spent 48 files (+234 −54); 12 of them were these same hook sites.

**Rule for feature branches:** `v2/addons-<name>` other than core touches zero paths that exist on upstream `main`. Allowed paths: `Tinycast/Features/Notchcast/<its folders>/**`, one line in `NotchcastRegistry.swift`, `Tests/nc-<its folders>-*.swift`, and appended `<Folder>: <file> ← <source> (<licence>)` lines in `notchcast/licenses/borrowed.md` for code it borrows (the file keeps its own notice; `NOTICE.md` points there). The gate derives this list from the registry lines and folder names the branch adds; nobody keeps a list of folders by hand. Anything else fails the gate. A feature that truly needs a new upstream hook stops and asks for a general hook in core.

H9 exists only for F10; if it is dropped, the budget falls to 9 files. F9 Alias and Space is dropped (maintainer decision, 2026-11-15), so there is no H10 and `RootPaletteView` stays untouched.

## 4. Settings

A **Notchcast** section in the stock Settings sidebar, right after Features (H6), with one tab per `NotchcastPane`, in order: Island (`notchcast-island`), Keyboard & Mouse (`notchcast-keyboard-mouse`), Display & Sound (`notchcast-display-sound`, its Display & Sound and Music sections), Capture (`notchcast-capture`), Launcher Extras (`notchcast-launcher`), Downloads (`notchcast-downloads`) and Mac Tweaks (`notchcast-mac-tweaks`); each opens from `tinycast://settings/<slug>`. Island always shows and holds `NotchcastIslandSettingsRows`, the island shell's own rows ("Show in screenshots and videos", "Outline when open", "Open on hover" and "Position on displays without a notch", each found by search on the Island tab). An add-on tab shows only while a registered switch sits in one of its categories: `NotchcastCore` installs the registered categories into `NotchcastPane` before Settings can open, so a tab never reads `AppCore`. Each tab is a stock grouped `Form`, one section per category it holds: a switch row per feature, then while it is on one row per command with its alias and hotkey fields and its own "Show in launcher" checkbox (on by default, stored as `launcherHiddenCommands` in the `<bundle id>.notchcast` suite; off drops the command from the launcher, its hotkey still works), and its extra rows, empty categories hidden. Settings › Commands does not list add-on commands. Categories are a fixed, ordered list in Core (one line each); add-ons pick one, and nobody maintains a list of features. Adding a category is one line in Core plus the tab that holds it; moving a feature is one word in its descriptor. A later add-on whose category has no tab adds one `NotchcastPane` case with its categories, slug, title and symbol arms, all in Core; `SettingsTab` stays untouched.

Settings search finds every switch with no line in the add-on: core installs one search row per switch from the descriptors (title, subtitle, id, and the names and keywords of the switch's commands, which hide while it is off), and each category header is the anchor its rows scroll to, on its own tab; each shown tab gets one pane row. **Add-on switches have no `SettingsFileKey`**, a deliberate exception to the settings-file rule: a switch can grant a capability (an event tap, Accessibility-gated input), and a capability flag is never carried by `settings.json` or a backup, as with `snippetsEnabled`. They live only in the `<bundle id>.notchcast` suite. The launcher's own Hide on an add-on command turns that checkbox off (`NotchcastLauncherHides`), and stock hides an earlier version left on an add-on command are dropped at start, since no checkbox could undo them. Add-on command aliases, hotkeys and launcher checkboxes are not carried by `settings.json` either: its commands binding lists only `CommandID` cases (`LauncherSettingsFile.swift`), so they stay in this Mac's preferences.

## 5. Proof

- **Delete test** `notchcast/check-addon-delete.py <Folder>|--rotate|--all`: in a scratch worktree, delete the folder, its registry line, its `borrowed.md` lines and `Tests/nc-<Folder>-*.swift`, regenerate the project, build Debug, run `Scripts/run-tests.sh`. It prints the step that failed and its log path; a tooling failure (load, timeout, xcodegen) is reported as a tooling failure, never as a contract breach. A READY for `v2/addons-<name>` runs it for each of its own folders and quotes the result. `ready-check.sh` runs `--rotate` (folder picked from HEAD's sha) after the build gates whenever the branch diff touches `Tinycast/Features/Notchcast/`, failing as `FAIL addon-delete`; other branches skip it and its extra Debug build. `--all` runs before every READY that changes Core, at one build per folder. A folder whose strings stay referenced elsewhere (`table: "Notchcast<Folder>"`) or whose add-on type has no registry line is a breach before any build. The scratch dir (`notchcast-delete.*` under `$NOTCHCAST_DELETE_SCRATCH` or the per-user temporary directory) holds `owner.pid`; SIGTERM, SIGINT or SIGHUP stops the running step's whole process group, removes the dir and exits 128+signal, and since SIGKILL skips that, every run first removes the dirs whose owner is dead and pid-less ones over an hour old. `--list` prints the folders at `--ref` and builds nothing. On CI, `gh workflow run delete-check.yml -f ref=<sha or branch>` runs the same check in one hosted `xcode-27` job (`.github/workflows/delete-check.yml`) that takes the folders in turn, about 15 minutes each: a failing folder never stops the rest, each prints its PASS/FAIL line, the logs are uploaded on failure, and the summary job lists folder → PASS, FAIL breach or FAIL tooling and fails if any folder did; `gh run view <id>` shows the table. The harnesses `CI_SKIP_TESTS` names are skipped there, as in every hosted run.
- **Reference guard** (every ready-check, all folders, no build): no file outside a folder names a top-level non-private type declared in it in code (strings and comments do not count), nor any of its switch ids, command slugs or entry ids as strings, except the registry line. This is what stops v1's drift to about ten one-line entries per feature in the core.
- **Footprint gate** (stack lead's ready-check line): core within the budget file; feature branches zero upstream paths, allowed paths derived from the registry.
- **Strings:** a build leaves upstream's `Localizable.xcstrings` byte-identical, and deleting a folder leaves no orphan string. With per-folder catalogs, a mechanical check fails on any add-on string that would be extracted into the stock table (a missed `table:`). If that check proves expensive, the fallback is plain English literals with no catalog (we ship English only); cost: no translation path later without touching every add-on.
- **Acceptance block** in every feature READY: (a) the user path proven by a live scene that does what the maintainer would do (press the key, see the result), not only a model harness; anything that cannot run here is NOT RUN and goes to the MBP; (b) "how to try it" in at most three plain lines for the maintainer; (c) which outside references it drew on (name, licence, what was taken). A feature the maintainer has not checked is "built, not accepted".
- **Registry harness** `Tests/nc-Notchcast-registry-test.swift`: ids and slugs unique and frozen: every switch id is either one of v1's raw values, all pinned in the harness bar the retired `keepAwake` and `lidClosedAwake`, or declared `// notchcast-new-switch-ids:` in its own folder, exact match (a declared id that is pinned, retired or no switch of that folder has fails), and no id is declared by two folders, every switch has a user path, every category valid and in exactly one shown tab, dependencies name known ids or are reported as absent, and every add-on that declares `commands` has an icon harness of its own (below).
- **Icon harness** `Tests/nc-<Folder>-command-icons-test.swift`, one per add-on with commands (#949): `// notchcast-kit: notchcast-command-icons`, `// notchcast-sources:` lines for the folder's descriptor and the Model and Service files it needs, stand-ins for its `live` systems and settings views, and `@main` calling `NotchcastCommandIconCheck.run(<Folder>Addon.self)` (`Tests/NotchcastCommandIconFixture.swift`): each command reaches the launcher index as a tile of its own real SF Symbol in its owner tab's tint, never the question mark. `Tests/nc-SmallCommands-command-icons-test.swift` is the shortest to copy.
- **Core harness** `Tests/nc-Notchcast-core-test.swift`: preferences on a scratch suite, module start/stop on toggle, tap order through the controller, hotkey key strings, presentation-seam recording, the tab → category map, which tabs show, unique slugs and their deep links, nc command entries owned by their add-on tab, and each switch drawing its commands' alias and hotkey fields. **Tap harness** `Tests/nc-Notchcast-tap-test.swift`: fake tap hub installed only while subscribed, resets, stale activations, liveness and the trust monitor. Both share `Tests/NotchcastTapFixtures.swift`. **Visibility harness** `Tests/nc-Notchcast-visibility-test.swift`: the stock Commands category never hides an add-on command or blocks its hotkey, against the real `VisibilityStore` and a stub `AppEntry`. **Alias harness** `Tests/nc-Notchcast-command-alias-test.swift`: shipped commands take an alias and a hotkey, stay reachable with Commands off, and their "Show in launcher" checkbox alone decides whether the launcher finds them by name and alias. **App proof** `addon-launcher` (`notchcast/app-proof.py`): the shipped wiring finds the first registered command needing no dependency or grant by name and alias over an earlier version's stock hide, and its checkbox off drops it on the same turn.

## 6. Why v1 needed untangling, and which rule prevents each cause

1. Every feature edited ~7 shared files (enum case, descriptor hub, `+All` commands, `command-slugs.txt`, settings groups, setting-row dispatch A–D, `NotchcastPreferences`). That took `merge=union` plus a 40-rule checker to repair merges. Prevented by §1: one registry line, no shared list.
2. The descriptor arrived late and stayed partial: commands, settings rows, observed prefs and modules stayed in the hub. The idea was sound; it was incomplete. Prevented by §2: the descriptor carries everything and the core wires it.
3. Feature logic lived inside upstream files: Alias Space in `RootPaletteView`, Number Keys reading `NotchcastPreferences.shared` in `LauncherScreen`, a link accessory in `LauncherCoordinator`, a Notes patch. 48 upstream files in all. Prevented by §3: hooks only in core, generic, and feature branches gated at zero.
4. Hooked upstream files named fork types, so upstream harnesses needed fork fixtures sourced into the upstream runner. Prevented by §3: hooks use stock types only.
5. Singletons and cross-feature glue (`NotchcastCore.<module>`, `AppCore.shared`, start-order wiring in the hub). Prevented by §2: `context` is the only door, and no add-on reads another.
6. 35 switches shipped with no user path. Prevented by the registry harness.
7. Renamed persisted ids needed legacy ids and migrations (Toggle Island). Prevented by frozen ids pinned in the registry harness.
8. Rebranding edits (About, URLs, Theme) mixed into the same upstream files. Outside add-ons; the stack lead's build-time string override owns them.
9. The root cause was process, not structure: 130 features built fast, 19 ended up switched on, none checked with the maintainer as it was built; harnesses tested code, not use; "behaviour stays the same" kept broken features broken in tidier folders. Prevented by the acceptance block in §5 and by not porting behaviour shown to be broken.

Verdict: v1's descriptor system was the right direction. The mess came from the central lists around it, from features writing into upstream files, and from building without the maintainer checking each feature.

# Notchcast add-ons: the contract

Every Notchcast feature on top of Tinycast is an add-on. An add-on plugs in with one line and comes out with one line, and syncing with upstream stays a non-event. This page says what an add-on may touch, what the core does for it, and how each promise is checked. It replaces v1's `feature-descriptors.md`, `command-hook.md` and `switch-paths.md`.

## 1. What an add-on is

- **One folder:** `Tinycast/Features/Notchcast/<Folder>/`. The folder holds every source the add-on needs. It may hold `Model/` (no AppKit or SwiftUI; every environment fact injected), `Service/`, `UI/` and `Settings/`, plus its own string catalog `<Folder>.xcstrings` (table `Notchcast<Folder>`, English only).
- **One registration line** in the fork-owned registry `Tinycast/Features/Notchcast/NotchcastRegistry.swift`, a single array with one `<Folder>Addon.self,` per line.
- **Its harnesses** live at `Tests/nc-<Folder>-*.swift`. `notchcast/harness_inputs.py` finds them by their header, so there is no list to edit.
- **Several switches in one folder** are allowed when they share code: Downloads + aria2 + Distill + Timestamps, Keep Awake + Lid Closed, Brightness + Volume (one media-key policy). They are then added and deleted together. Two folders never share code; if both need something, it moves into Core as a service with a reason.
- **Nothing else.** An add-on edits no upstream file, no other add-on, no Core file, no shared list, no `Localizable.xcstrings` and no generated file (`Tinycast.xcodeproj` is regenerated by CI and never committed).

## 2. What the descriptor declares (the core does the wiring)

`<Folder>Addon` conforms to `NotchcastAddon` and states, as plain data:

- `switches`: one per user-facing feature: frozen string id (the v1 raw value where one exists), title, subtitle, `category`, `defaultEnabled`, `dependencies` (switch ids, may name another folder's switch: the core then turns it off when that folder is gone), `requiredGrants`.
- `commands`: launcher commands, each with id `command:nc-<slug>` (frozen), name, symbol, owning switch, `run`. They appear as ordinary launcher entries of the existing `AppEntry.Kind.command`, so there is no new launcher section and no category guessed from an id.
- `hotKeys`: commands may be bound like any built-in command, stored at `hotkey.command:nc-<slug>`, the same key v1 used, so existing `nc-screenshot-area` and `nc-screenshot-display` bindings resolve unchanged.
- `settings`: extra rows under each switch, written as SwiftUI views inside the folder; the core renders them in the add-on's category section.
- `taps`: event-tap subscriptions (event mask plus handler). The core installs one shared tap only while at least one enabled switch subscribes, and removes it when the last unsubscribes. Subscribed does not mean live: an add-on that acts outside its handlers checks `context.isTapLive`, and each tap's `reset` runs when the tap drops on its own.
- `makeModule(context)`: start and stop. The core builds the module when the switch and its dependencies are on and stops it when they go off. `context` is the only door to the app: preferences store, presentation seam (island), tap hub, launcher hooks, Core services (root helper client, process runner, clock). An add-on never reads `AppCore`, `NotchcastCore` statics or another add-on.

**Presentation** is the island's own API: `context.presenter` is `any IslandPresenting`, and add-ons post the Island value types (`IslandLevel`, `IslandNotice`, `IslandStatus`, `IslandMenuRow`; notchcast/docs/island-shell.md "Presentation API"). Until the island's live states render notices, `NotchcastCore` hands the controller `NotchcastHUDPresenter`, a temporary stand-in: notices go to the stock HUD (a failure in the danger tone, a notice with `progress` as the progress HUD), and levels, status and menu rows are dropped. Retiring it is one line in `NotchcastCore.init`, `NotchcastHUDPresenter(core: core)` becoming `core.islandPresenter`, plus deleting the file.

A switch with none of commands, settings action, taps or a module has no user path and fails the registry harness (v1 shipped 35 such switches).

**Ownership.** There is one `NotchcastCore` instance, created by H1 inside `AppCore.start` and held by `AppCore`; it stops every module and removes the tap when the app terminates. Hook statics in upstream files are `@MainActor`, set once in `start`, and `nil` means stock behaviour. No second actor, no new `MainActor.assumeIsolated`.

**Debug scenes and probes** of an add-on live in its folder, so the delete test removes them. Nothing of an add-on goes into `IslandVerification` or any other shared scenes file.

## 3. Upstream hooks: the whole footprint of the add-on system

Only `v2/addons-core` touches upstream files, and only through these hooks. Each hook is a general injection point declared with stock types (a closure or static the core sets in `start`). No upstream file a harness compiles names a fork type. One upstream harness needs a fixture all the same: `Tests/AppInstallationTests.swift` stubs `HotKeyAction` and compiles `VisibilityStore.swift`, so its stub carries H4's case (+1); the dummy delete test found it.

| # | Upstream file | Hook | Lines |
| - | - | - | - |
| H1 | `App/AppCore.swift` | `NotchcastCore.start(self)` in `start()` | +1 |
| H2 | `Launcher/Model/CommandCatalog.swift` or `Launcher/Service/AppIndex.swift` | append add-on entries, filtered by `isEnabled` | +3 |
| H3 | `Launcher/UI/LauncherCoordinator.swift` | dispatch an add-on entry before stock dispatch | +1 |
| H4 | `HotKeys/Model/HotKeyAction.swift` (+`+EntryID.swift`) | `case notchcastCommand(entryID:)`, its `defaultsKey` arm and entry mapping; stock `.command(CommandID)` cannot carry it without new `CommandID` cases | +4 |
| H5 | `HotKeys/Service/HotKeyManager.swift` | list, name, perform, register only while the owning switch is on | +5 |
| H6 | `Settings/SettingsTab.swift` | `case notchcast`, last, so it sits at the bottom of the sidebar; its slug/title/icon arms | +5 |
| H7 | `Settings/SettingsDetailView.swift` | its detail arm | +2 |
| H8 | `Settings/SettingsSearchCatalog.swift` | append `NotchcastSettingsSearch.entries`: the pane row plus one row per add-on switch | +1 −1 |
| H9 | `Launcher/UI/LauncherScreen.swift` | `static var digitRow`: ⌘1–⌘0 ask core for a row first (digit, query, entry rows); nil keeps the stock favourite | +5 −1 |

H2 names the one file actually used once built. H4 and H6 add cases to upstream enums. Known cost: a future upstream exhaustive `switch` over `HotKeyAction` or `SettingsTab` breaks our build with no textual conflict; the sync rehearsal's ready-check is what catches it. Every upstream exhaustive switch that needed an arm is listed in this table and counts in the budget.

**Budget for `v2/addons-core` is a gate.** The numbers (files, +lines, −lines) live in one fork-owned file, `notchcast/addons-budget.env`; ready-check fails `v2/addons-core` above them. Raising the budget is a visible one-line change with the reason in the commit body. Starting estimate 10 files, +34 −5 (F9 and its H10 dropped 2026-11-15); the env file now holds the real footprint of the first READY. `notchcast/check-addons.py` runs in `ci-build.sh` (so in ready-check and CI): core mode prints each upstream path with its +/− and fails above the budget; feature mode fails any path outside the branch's folders, its tests and `<Type>.self,` registry lines; `--mode` (core, feature or none) or `--branch` is required, and `ci-build.sh` passes the branch, which is core only for exactly `v2/addons-core` or `v2/addons-core-<n>` (the name a rebased core is pushed under since nothing force-pushes), feature for any other `v2/addons-*`; on every branch a reference guard fails a fork-added line outside an add-on's folder that names its switch ids or slugs, or names one of its top-level types in code (strings, comments and nested types do not count; its registry line, other add-ons' `dependencies:` arrays and the core harnesses `Tests/nc-Notchcast-*.swift`, which pin the frozen ids, are exempt). v1 spent 48 files (+234 −54); 12 of them were these same hook sites.

**Rule for feature branches:** `v2/addons-<name>` other than core touches zero paths that exist on upstream `main`. Allowed paths: `Tinycast/Features/Notchcast/<its folders>/**`, one line in `NotchcastRegistry.swift`, `Tests/nc-<its folders>-*.swift`, and appended `<Folder>: <file> ← <source> (<licence>)` lines in `notchcast/licenses/borrowed.md` for code it borrows (the file keeps its own notice; `NOTICE.md` points there). The gate derives this list from the registry lines and folder names the branch adds; nobody keeps a list of folders by hand. Anything else fails the gate. A feature that truly needs a new upstream hook stops and asks for a general hook in core.

H9 exists only for F10; if it is dropped, the budget falls to 9 files. F9 Alias and Space is dropped (maintainer decision, 2026-11-15), so there is no H10 and `RootPaletteView` stays untouched.

## 4. Settings

One upstream entry, **Notchcast**, at the bottom of the stock Settings sidebar (H6). Inside it is our own Form, one section per category, generated from the descriptors: a switch row per feature, its extra rows under it, empty categories hidden. Categories are a fixed, ordered list in Core (one line each); add-ons pick one, and nobody maintains a list of features. Adding a category is one line in Core; moving a feature is one word in its descriptor.

Settings search finds every switch with no line in the add-on: core installs one search row per switch from the descriptors (title, subtitle, id, and the names and keywords of the switch's commands, which hide while it is off), and each category header is the anchor its rows scroll to. **Add-on switches have no `SettingsFileKey`**, a deliberate exception to the settings-file rule: a switch can grant a capability (an event tap, Accessibility-gated input), and a capability flag is never carried by `settings.json` or a backup, as with `snippetsEnabled`. They live only in the `<bundle id>.notchcast` suite.

## 5. Proof

- **Delete test** `notchcast/check-addon-delete.py <Folder>|--rotate|--all`: in a scratch worktree, delete the folder, its registry line, its `borrowed.md` lines and `Tests/nc-<Folder>-*.swift`, regenerate the project, build Debug, run `Scripts/run-tests.sh`. It prints the step that failed and its log path; a tooling failure (load, timeout, xcodegen) is reported as a tooling failure, never as a contract breach. A READY for `v2/addons-<name>` runs it for each of its own folders and quotes the result. It is standalone: `ready-check.sh` does not run it (lead decision 2026-11-15), so a READY that touches `Tinycast/Features/Notchcast/` quotes `--rotate` (folder picked from HEAD's sha) itself, and `--all` runs before every READY that changes Core, at one build per folder. A folder whose strings stay referenced elsewhere (`table: "Notchcast<Folder>"`) or whose add-on type has no registry line is a breach before any build.
- **Reference guard** (every ready-check, all folders, no build): no file outside a folder names a top-level non-private type declared in it in code (strings and comments do not count), nor any of its switch ids, command slugs or entry ids as strings, except the registry line. This is what stops v1's drift to about ten one-line entries per feature in the core.
- **Footprint gate** (stack lead's ready-check line): core within the budget file; feature branches zero upstream paths, allowed paths derived from the registry.
- **Strings:** a build leaves upstream's `Localizable.xcstrings` byte-identical, and deleting a folder leaves no orphan string. With per-folder catalogs, a mechanical check fails on any add-on string that would be extracted into the stock table (a missed `table:`). If that check proves expensive, the fallback is plain English literals with no catalog (we ship English only); cost: no translation path later without touching every add-on.
- **Acceptance block** in every feature READY: (a) the user path proven by a live scene that does what the maintainer would do (press the key, see the result), not only a model harness; anything that cannot run here is NOT RUN and goes to the MBP; (b) "how to try it" in at most three plain lines for the maintainer; (c) what was deliberately changed from v1 and why. A feature the maintainer has not checked is "built, not accepted".
- **Registry harness** `Tests/nc-Notchcast-registry-test.swift`: ids and slugs unique and frozen: every switch id is either a pinned v1 raw value or named in the harness's `newIDs`, exact match, and no id is declared by two folders, every switch has a user path, every category valid, dependencies name known ids or are reported as absent.
- **Core harness** `Tests/nc-Notchcast-core-test.swift`: preferences on a scratch suite, module start/stop on toggle, fake tap hub installed only while subscribed, hotkey key strings, presentation-seam recording.

## 6. Why v1 needed untangling, and which rule prevents each cause

1. Every feature edited ~7 shared files (enum case, descriptor hub, `+All` commands, `command-slugs.txt`, settings groups, setting-row dispatch A–D, `NotchcastPreferences`). That took `merge=union` plus a 40-rule checker to repair merges. Prevented by §1: one registry line, no shared list.
2. The descriptor arrived late and stayed partial: commands, settings rows, observed prefs and modules stayed in the hub. The idea was sound; it was incomplete. Prevented by §2: the descriptor carries everything and the core wires it.
3. Feature logic lived inside upstream files: Alias Space in `RootPaletteView`, Number Keys reading `NotchcastPreferences.shared` in `LauncherScreen`, a link accessory in `LauncherCoordinator`, a Notes patch. 48 upstream files in all. Prevented by §3: hooks only in core, generic, and feature branches gated at zero.
4. Hooked upstream files named fork types, so upstream harnesses needed fork fixtures sourced into the upstream runner. Prevented by §3: hooks use stock types only.
5. Singletons and cross-feature glue (`NotchcastCore.<module>`, `AppCore.shared`, start-order wiring in the hub). Prevented by §2: `context` is the only door, and no add-on reads another.
6. 35 switches shipped with no user path. Prevented by the registry harness.
7. Renamed persisted ids needed legacy ids and migrations (Toggle Island). Prevented by frozen ids pinned in the registry harness.
8. Rebranding edits (About, URLs, Theme) mixed into the same upstream files. Outside add-ons; the stack lead's build-time string override owns them.
9. The root cause was process, not structure: 130 features built fast, 19 ended up switched on, none checked with the maintainer as it was built; harnesses tested code, not use; "behaviour stays the same" kept broken features broken in tidier folders. Prevented by the acceptance block in §5 and by not porting behaviour shown to be broken.

Verdict: v1's descriptor system was the right direction. The mess came from the central lists around it, from features writing into upstream files, and from building without the maintainer checking each feature.
